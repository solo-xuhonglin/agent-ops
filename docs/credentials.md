## 1. Agent 是外部系统里的一个员工

**在外部系统里开一个专给 Agent 用的账号，把它登记到平台。**

换来四件事：

| | Agent 专用账号 | 调用时把凭据传进来 |
|---|---|---|
| 外部系统看到谁 | Agent 自己 | 调用方 / 终端用户本人 |
| **SDK 契约** | **干净** —— 调用方不知道凭据的存在 | 泄漏凭据需求，**加一个工具等于改对外契约** |
| 前端可用 | ✅ | ❌ 浏览器里没有外部系统的凭据 |
| 重投 | ✅ 凭据本来就在 | 需要持久化，否则重投的 worker 手上什么都没有 |

**代价是外部系统分不清"谁在操作"** —— 张三和李四调同一个 Agent，对方看到的都是同一个账号。这正是终端用户标识只作审计、不参与判权的原因（见 [permissions.md](./permissions.md) 2.3）。

> **换来的边界也很实在**：Agent 在外部系统里能做什么，由那个账号的权限一次性划定，看得见、管得住 —— 这是最小权限真正能落地的地方。

---

## 2. 归租户所有

**凭据由租户管理员登记，不是平台运维统一配。** 它是租户自己的一行数据，多租户隔离因此天然成立 —— 不靠进程环境变量。

Agent、工具与 Skill **都按租户隔离**：一个租户看不到、也用不到另一个租户的任何配置。

---

## 3. 工具声明，Agent 提供

- **工具**描述"怎么调"这个外部接口，并**声明它需要一份凭据**
- **Agent** 在挂载工具时决定**用哪一份**

一份凭据因此可以被多个工具、多个 Agent 复用；而"以谁的权限调外部系统"由 Agent 决定 —— **权限边界跟着 Agent 走**。理由在权限那一侧：Agent 才是承担对外责任、声明对外开放范围的东西，工具只是共享能力。

> 一个租户只配一份凭据、所有 Agent 都用它，就退化成"一份凭据挂全租户"。

---

## 4. 存储与取用

**凭据加密存储，明文不落库、不进导出文件、不进 trace。**

加密要一把主密钥，它放在部署环境里（单机 `docker-compose` 用一个 docker secret）。**问题因此收敛成一把密钥**，而不是每个外部系统各一把散在各个节点上 —— 但主密钥本身怎么轮换、怎么托管，v1 没有方案，见 [roadmap.md](./roadmap.md)。

**执行时由 `runtime` 按租户取用、解密、发给外部系统。** 一次运行内多次使用同一份凭据，只在内存里留到运行结束。

---

## 5. 尽量要长期令牌，不要账号密码

密码是给**人**设计的 —— 绑人、可能强制 MFA、有到期策略，随时会因为对方的安全策略失效。API token / OAuth client credentials 才是给机器用的：可吊销、可限权、可设到期。

**外部系统只提供账号密码时，只能存密码 —— 但要知道它什么时候会突然坏掉。**
