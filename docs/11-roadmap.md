## 1. 路线图

小步迭代：每个单元以可运行的测试收口，顺序即依赖序。已完成：骨架（六容器 Docker 拓扑）、单元 1（config 接库）、单元 2（shared spec 模型与事件词汇表、按写者建表、种子）、单元 3（contract v1 + manager HTTP 面）、单元 4（内部协议 + worker 桩执行）。阶段 A 先垂直打通 SDK 链路——worker 先用桩执行（直接落 `run_started` / `run_finished`），链路立住后在阶段 B 换成真引擎；快照、key、租户等由种子数据落库，配置系统（10–16）建成后由真实流程逐个替换种子。

### 阶段 A：SDK 链路

| # | 单元 | 验证 |
|---|---|---|
| 2 | `shared/`：Agent（ReAct）spec 模型与输入声明、运行日志与事件词汇表；各服务按写者归属建表、种子数据落库 | 序列化 round-trip；配对不变式测试 |
| 3 | `contract/` 第一版 + `manager` HTTP 面：永久 key 鉴权、params 校验、会话租约、submit 落库（幂等）、get / cancel | API 测试，含幂等重放返回同一 Run |
| 4 | 内部协议 + worker 桩执行：常驻连接（报到、心跳、dispatch、cancel）、epoch、巡检；桩执行不调模型，直接落日志 | 集成测试：submit → worker 落日志 → Run 到终态 |
| 5 | 事件推流：Run 连接、SSE 订阅、订阅补发、断线重连、周期 state | 断线重连不丢持久事件 |
| 6 | 两个 SDK 并列收口：后端 Python 与前端 TypeScript，方法一一对应，句柄语义（wait / stream）、错误映射（临时 key 靠后，直连即测） | 两个 SDK 的端到端冒烟：submit → 桩执行 → 事件流回 SDK |

## 2. 待定项

1. **DAG 的编辑形态。** v1 用表单与 JSON 编辑图结构，不做拖拽画布。但图一旦超过十来个节点，手写边就不现实了 —— **画布什么时候补，取决于第一个真实 DAG 的规模**。
2. **账号的口令形式。** 账号体系本身已经定了 —— 平台级账号、邀请加入、开租户是运维动作（见 [03-domain-model.md](./03-domain-model.md) 2.6）。未定的是**口令怎么存**：本地校验，还是接一个轻量目录。v1 不做单点登录。
3. **权限模型何时升级到工具级。** 触发条件：第一个外部调用方调用一个会写外部系统的 Agent。见 [10-permissions.md](./10-permissions.md) 第 3 节。
4. **永久 key 何时放开成多把。** v1 一个 Agent 一把，所有后端调用方共用，出了事分不清是谁。放开成多把（每把可命名、可单独停用）的时机，取决于第一次出现"同一个 Agent 被多个外部系统调用、且需要区分"的场景。见 [10-permissions.md](./10-permissions.md) 2.1。
5. **凭据的主密钥怎么托管与轮换。** 凭据在库里加密存储，靠部署环境里的一把主密钥（见 [09-credentials.md](./09-credentials.md) 第 4 节）。**轮换主密钥意味着把全部凭据重新加密**，这个操作没有方案；将来多环境部署时，托管方式也要重定。
6. **发布是否需要审批流。** 失去 Git PR review 后，如果仍需要"变更需批准"，建议在发布领域加可选的审批步骤。
7. **子 Agent 嵌套深度上限取多少。** 环检测保证无环，但不保证浅。建议 8 层，具体值应等真实嵌套场景出现后再定。见 [04-orchestration.md](./04-orchestration.md) 第 4 节。
8. **读模型的更新方式。** 同步触发（与写同事务）还是异步事件驱动？前者简单但写入变慢，后者快但有延迟。
9. **ReAct 的可解释性如何缓解。** 灵活性带来的不可解释性只能缓解、不能消除。可选做法：在运行日志里额外记录每轮的工具选择理由。这能回答"它做了什么"，但回答不了"它为什么没做另一件事"。见 [04-orchestration.md](./04-orchestration.md) 1.2。
10. **哪些流程该从 ReAct 迁到 DAG。** 有了两种模式，"什么时候该迁"就成了一个真实的运维决策 —— 迁移的判据、由谁判定、迁移时怎么保持行为一致，目前没有标准。见 [04-orchestration.md](./04-orchestration.md) 1.3。
11. **生产环境的日常变更是否改走数据库。** 环境稳定之后，变更可能主要靠直接的 SQL 变更，平台的编辑与发布退化为测试与应急手段（见 [07-release.md](./07-release.md) 第 3 节）。**这条路绕开版本、审计与快照** —— 改了库里的行，不产生新版本、不进审计、不更新发布记录。届时得先回答"怎么记录、怎么防止漂移"，v1 不设计。
12. **步骤重试的上限与退避。** 重投是 at-least-once，未完成的那一步会被重试（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 5 节）。超过上限就把 Run 判失败 —— 具体几次、要不要退避，等真实故障率出来再定。
13. **`manager` 什么时候拆开。** 它同时管连接、派发与对外契约，变更驱动不是单一的（见 [01-agent-platform-design.md](./01-agent-platform-design.md) 第 5 节）。更干净的切法是拆成 `hub`（连接与消息，不认识领域）与 `dispatcher`（派发与运行状态）—— **什么时候拆，取决于哪一样先变成瓶颈**。
14. **`manager` 什么时候多副本。** v1 一个副本（见 [01-agent-platform-design.md](./01-agent-platform-design.md) 2.3）。多个副本要补三样：副本之间一条长连接、一张 `run → manager` 的路由表、一份副本成员视图。而 `06` §2.5 那个「等 `worker` 连上再巡检」的门控在多副本下不成立 ——「第一个连上」不等于「都连上了」。**在那之前，`manager` 重启这一段时间里没有别人接管，全平台的连接一起断。**
15. **心跳里的进度要不要用于判死。** 心跳能证明连接还在，证明不了"这一步在推进"（见 [06-internal-protocol.md](./06-internal-protocol.md) 2.1）。要判断卡死得靠"这一步跑了多久"，但**一次正常的慢调用和一次卡死长得一模一样** —— 据它重投会把正常运行反复打断，取值有多大余地没有标准。
16. **巡检周期与状态推送间隔取多少。** 前者决定一个 Run 无人接管多久才被发现；后者要小于链路上最短的超时（nginx 的 `proxy_read_timeout` 默认 60 秒），又不能太吵。见 [06-internal-protocol.md](./06-internal-protocol.md) 1.1 与 2.5。
