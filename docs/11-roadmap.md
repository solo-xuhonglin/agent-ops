## 1. 路线图

小步迭代：每个单元以可运行的测试收口，顺序即依赖序。已完成：骨架（六容器 Docker 拓扑）、单元 1（config 接库）、单元 2（shared spec 模型与事件词汇表、按写者建表、种子）、单元 3（contract v1 + manager HTTP 面）、单元 4（内部协议 + worker 桩执行）、单元 5（事件推流）、单元 6（两个 SDK 并列收口）—— 阶段 A 完成；单元 7（ReAct 引擎：手写循环、fake LLM、流式增量、日志重建续跑）、单元 8（上下文压缩：阈值触发 LLM 摘要、context_compacted 落库不外发、重建从标记重启）、单元 9（HTTP 工具：Tool spec 模型、参数模板、凭据占位（v1 解析器=环境变量 `CREDENTIAL_<名称>`，单元 14 换 secrets 存储）、响应裁剪按字节、幂等键 `run_id:action_id`、工具循环与 max_iterations）—— 阶段 B 完成；单元 10（`config` API 骨架：最小账号表（Argon2id 口令）、登录会话（HttpOnly Cookie、7 天滑动、多端并发）、RBAC 最低角色依赖（判权实时读成员关系）、种子管理员、`/api/` 边缘分流）—— 阶段 C 骨架先行，iam 领域顺延为单元 12（各领域单元自带配置 UI 页面）、`audit` 追加随之落地。worker 的模型调用当前只有 fake provider（`LLM_PROVIDER` 默认 `fake`），真实 provider 适配随配置与凭据阶段落地；快照、key、租户、管理员等由种子数据落库，配置系统（10–17）建成后由真实流程逐个替换种子。

## 2. 待定项

1. **DAG 的编辑形态。** v1 用表单与 JSON 编辑图结构，不做拖拽画布。但图一旦超过十来个节点，手写边就不现实了 —— **画布什么时候补，取决于第一个真实 DAG 的规模**。
2. **权限模型何时升级到工具级。** 触发条件：第一个外部调用方调用一个会写外部系统的 Agent。见 [10-permissions.md](./10-permissions.md) 第 3 节。
3. **永久 key 何时放开成多把。** v1 一个 Agent 一把，所有后端调用方共用，出了事分不清是谁。放开成多把（每把可命名、可单独停用）的时机，取决于第一次出现"同一个 Agent 被多个外部系统调用、且需要区分"的场景。见 [10-permissions.md](./10-permissions.md) 2.1。
4. **凭据的主密钥怎么托管与轮换。** 凭据在库里加密存储，靠部署环境里的一把主密钥（见 [09-credentials.md](./09-credentials.md) 第 4 节）。**轮换主密钥意味着把全部凭据重新加密**，这个操作没有方案；将来多环境部署时，托管方式也要重定。
5. **发布是否需要审批流。** 失去 Git PR review 后，如果仍需要"变更需批准"，建议在发布领域加可选的审批步骤。
6. **子 Agent 嵌套深度上限取多少。** 环检测保证无环，但不保证浅。建议 8 层，具体值应等真实嵌套场景出现后再定。见 [04-orchestration.md](./04-orchestration.md) 第 4 节。
7. **读模型的更新方式。** 同步触发（与写同事务）还是异步事件驱动？前者简单但写入变慢，后者快但有延迟。
8. **ReAct 的可解释性如何缓解。** 灵活性带来的不可解释性只能缓解、不能消除。可选做法：在运行日志里额外记录每轮的工具选择理由。这能回答"它做了什么"，但回答不了"它为什么没做另一件事"。见 [04-orchestration.md](./04-orchestration.md) 1.2。
9. **哪些流程该从 ReAct 迁到 DAG。** 有了两种模式，"什么时候该迁"就成了一个真实的运维决策 —— 迁移的判据、由谁判定、迁移时怎么保持行为一致，目前没有标准。见 [04-orchestration.md](./04-orchestration.md) 1.3。
10. **生产环境的日常变更是否改走数据库。** 环境稳定之后，变更可能主要靠直接的 SQL 变更，平台的编辑与发布退化为测试与应急手段（见 [07-release.md](./07-release.md) 第 3 节）。**这条路绕开版本、审计与快照** —— 改了库里的行，不产生新版本、不进审计、不更新发布记录。届时得先回答"怎么记录、怎么防止漂移"，v1 不设计。
11. **步骤重试的上限与退避。** 重投是 at-least-once，未完成的那一步会被重试（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 5 节）。超过上限就把 Run 判失败 —— 具体几次、要不要退避，等真实故障率出来再定。
12. **`manager` 什么时候拆开。** 它同时管连接、派发与对外契约，变更驱动不是单一的（见 [01-agent-platform-design.md](./01-agent-platform-design.md) 第 5 节）。更干净的切法是拆成 `hub`（连接与消息，不认识领域）与 `dispatcher`（派发与运行状态）—— **什么时候拆，取决于哪一样先变成瓶颈**。
13. **`manager` 什么时候多副本。** v1 一个副本（见 [01-agent-platform-design.md](./01-agent-platform-design.md) 2.3）。多个副本要补三样：副本之间一条长连接、一张 `run → manager` 的路由表、一份副本成员视图。而 `06` §2.5 那个「等 `worker` 连上再巡检」的门控在多副本下不成立 ——「第一个连上」不等于「都连上了」。**在那之前，`manager` 重启这一段时间里没有别人接管，全平台的连接一起断。**
14. **心跳里的进度要不要用于判死。** 心跳能证明连接还在，证明不了"这一步在推进"（见 [06-internal-protocol.md](./06-internal-protocol.md) 2.1）。要判断卡死得靠"这一步跑了多久"，但**一次正常的慢调用和一次卡死长得一模一样** —— 据它重投会把正常运行反复打断，取值有多大余地没有标准。
15. **巡检周期与状态推送间隔取多少。** 前者决定一个 Run 无人接管多久才被发现；后者要小于链路上最短的超时（nginx 的 `proxy_read_timeout` 默认 60 秒），又不能太吵。见 [06-internal-protocol.md](./06-internal-protocol.md) 1.1 与 2.5。

16. **统一编译是否引入 LangGraph。** 触发条件：DAG（单元 21）落地。手写循环已承载 ReAct；LangGraph 的价值在图结构与检查点，而运行真相源是本平台的运行日志，检查点与之重叠。引入前先回答「图编译换来什么手写循环给不了」。
17. **`window_ratio` 何时生效。** 压缩的窗口占比阈值需要 model_id→窗口大小映射，只有真实 provider 能带来；当前仅 `token_limit` 触发，token 数按字符估算（len//4）。
18. **A2A / AG-UI 边缘 adapter 要不要做。** 事件词汇已对齐 AG-UI 的 UI 路径（docs/02 §6.5）；接入生态还需要边缘端点 —— A2A adapter（Task↔Run、`message:stream`↔SSE 订阅）与 AG-UI `HttpAgent` 端点（POST `RunAgentInput` → AG-UI 事件流）。内部零改动、纯接入层；**做的时机取决于第一个外部 agent 生态或现成 UI 组件要直连的需求**。注意两者的输入模型（客户端携带 tools/state）与「配置在平台、key 决定身份」不同，adapter 里要做映射取舍。
