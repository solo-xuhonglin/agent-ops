## 1. 路线图

| 里程碑 | 内容 |
|---|---|
| M1 | 协议定义 + 共享 spec 模型 + 校验器 |
| M2 | `config`：身份与审计领域 |
| M3 | `config`：定义领域（工具 / Skill）+ 管理 API |
| M4 | `config`：Agent 定义（ReAct）+ 发布领域 |
| M5 | `runtime`：ReAct 编译与执行 + HTTP 工具 |
| M6 | `gateway` + 后端 Python SDK |
| M7 | Python 工具沙箱 |
| M8 | Skill 渐进加载 |
| M9 | `config`：DAG 编辑 + `runtime` DAG 编译 |
| M10 | 子 Agent（声明、环检测、嵌套运行） |
| M11 | 前端 TypeScript SDK |
| M12 | 观测：trace 查询、Playground、成本 |

覆盖 M1–M12，规模超出单个实现计划。**每个里程碑应产出各自独立的实现计划**，按顺序推进；M1 是其余一切的前置依赖。

## 2. 待定项

1. **DAG 的编辑形态。** v1 用表单与 JSON 编辑图结构，不做拖拽画布。但图一旦超过十来个节点，手写边就不现实了 —— **画布什么时候补，取决于第一个真实 DAG 的规模**。
2. **平台成员的认证方式。** v1 不做单点登录，账号由平台自己管 —— 具体是本地密码还是接一个轻量目录，尚未定。**这不影响其他设计**：配置面与调用面本来就互不打通（见 8.1）。
3. **权限模型何时升级到工具级。** 触发条件：第一个外部应用调用一个会写外部系统的 Agent。见 8.3。
4. **凭据管理何时加回。** 见 7.2 的风险表 —— 四项缺失全是真实的安全债。建议不晚于"单 runtime 承载多租户"那一刻。
5. **发布是否需要审批流。** 失去 Git PR review 后，如果仍需要"变更需批准"，建议在发布领域加可选的审批步骤。
6. **定义域是否该再分子域。** Tool / Skill / Agent 合为一域的理由是三者同属一类事物；但它们的**所有者可能不同**（集成工程师写 tool，领域专家写 skill，产品改 agent），按所有权标准可以再拆。
7. **子 Agent 嵌套深度上限取多少。** 环检测保证无环，但不保证浅。建议 8 层，具体值应等真实嵌套场景出现后再定。见 [orchestration.md](./orchestration.md) 第 4 节。
8. **读模型的更新方式。** 同步触发（与写同事务）还是异步事件驱动？前者简单但写入变慢，后者快但有延迟。
9. **ReAct 的可解释性如何缓解。** 灵活性带来的不可解释性只能缓解、不能消除。可选做法：在 trace 里额外记录每轮的工具选择理由。这能回答"它做了什么"，但回答不了"它为什么没做另一件事"。见 [orchestration.md](./orchestration.md) 1.2。
10. **哪些流程该从 ReAct 迁到 DAG。** 有了两种模式，"什么时候该迁"就成了一个真实的运维决策 —— 迁移的判据、由谁判定、迁移时怎么保持行为一致，目前没有标准。见 [orchestration.md](./orchestration.md) 1.3。
