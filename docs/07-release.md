## 1. 编辑与发布

编辑发生在**领域实体**上（草稿态），不在发布域。每个实体带乐观锁版本号，并发修改冲突时返回冲突并展示字段级差异，供人工合并。

发布是**快照**：把领域实体序列化为不可变快照，版本号单调递增，写入发布域。归档只是标记，不物理删除。

**快照只含配置** —— 编排结构、能力挂载、子 Agent 引用、上下文策略，以及挂载到的 Tool / Skill 的**版本号**。**不含**调用 key、责任人、归档标志。

> 这些字段各自独立变化：重置一把 key、换一个责任人，都不该产生新版本，更不该被回滚带回旧值。

**编辑的并发与发布的并发是两件事**，分别由实体上的锁版本与发布记录上的状态承担，不混在一起。

**快照是运行的前提** —— 会话与 Run 都绑定已发布的版本，历史执行因此可精确复现（见 [03-domain-model.md](./03-domain-model.md) 2.7）。唯一的例外是**凭据**：它不进快照，运行时取活的那一份。

## 2. 版本对比

两个快照之间做结构化 JSON diff —— 结构由 schema 确定，因此可以渲染成字段级对比而非文本对比。

## 3. 跨环境迁移

**开发、预生产、生产是三套独立部署**，各有一套 `docker-compose`、一个数据库、一批调用 key 与凭据。**平台内部没有环境这一层** —— 环境是部署边界，不是数据模型里的一列。

配置在环境之间靠**导入导出**搬。导出的是结构化快照，不是数据库 dump：ID 在环境之间必然不同，因此**引用在边界翻译成业务标识**，导入时再解析回本地 ID。

**两样东西刻意不跨环境：**

| | 为什么不搬 |
|---|---|
| 调用 key | key 各环境独立。把它搬过去，等于把一个环境的调用权限复制到另一个环境 |
| 凭据 | 生产的外部账号不该出现在开发环境，反之亦然。**导出的文件里绝不能出现凭据明文** |

**导入时缺凭据就报错**，并列出缺哪几个，由操作人先在目标环境登记好再导。**不自动绑定、不静默跳过** —— 一个引用不到凭据的 Agent 上了线，要等第一次被调用才炸。

> 导入导出由管理员执行，见 [10-permissions.md](./10-permissions.md) 第 1 节。**在环境之间，平台的编辑与发布退居测试与应急手段**；环境稳定之后的日常变更路径见 [11-roadmap.md](./11-roadmap.md) 待定项 11。
