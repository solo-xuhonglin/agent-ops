## 1. 三类连接

| 连接 | 方向 | 单位 | 承载 |
|---|---|---|---|
| `manager` ↔ 客户端 | 单向（服务端推） | **会话** | 事件与状态。**只读**（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 4 节） |
| `manager` ↔ `worker` | 双向 | **`worker`** | 下行：派发、取消。上行：心跳、状态、事件 |
| `manager` ↔ `manager` | 双向 | 副本 | 事件路由与转发 |

**内部双向，外部单向** —— 所以两侧用不同的东西。客户端侧是 SSE（纯 HTTP，SDK 里不需要协议代码）；内部侧是自造的长连接协议。

**客户端侧的单位是会话，不是 Run。** 会话才是界面的单位，而且**空闲时也要有连接** —— 否则另一个标签页提交的 Run 推不进来。

**`manager` ↔ `worker` 的单位是 `worker`** —— 一个 worker 一条。报到与心跳是 worker 级的事实（能跑什么、还有多少空闲额度），按 Run 拆它们就没有落脚点。派发、取消、事件都带 `run_id`，在同一条上多路复用；同一个 Run 的事件天然保序，跨 Run 不需要保序。

### 1.1 保活与心跳

**三类连接都需要保活；只有一类有应用层心跳。**

| 连接 | 保活 | 应用层心跳 |
|---|---|---|
| 客户端 ↔ `manager` | ✅ —— `manager` 发注释行 | ❌ |
| `manager` ↔ `worker` | ✅ | ✅ 带状态，见 2.1 |
| `manager` ↔ `manager` | ✅ | ❌ —— 单副本下这条连接不存在 |

**保活是传输层的空包**（SSE 注释行）—— 单向、不带语义、不需要回应。它防的是中间层把空闲连接掐掉（nginx 的 `proxy_read_timeout` 默认 60 秒，而一个慢步骤可能几十秒没有事件）。间隔要小于链路上最短的那个超时。

**它同时也是活着的证明**：客户端一段时间没收到任何字节就重连。**误判的代价只是重连一次** —— 游标是幂等的，重放不会错。这和 `epoch` 是同一个形状：**代价是浪费，不是错误。**

**心跳是另一回事** —— 应用层协议消息、双向、带状态，只存在于 `manager` ↔ `worker`。客户端侧没有它：界面要的那个状态（空闲 / 在跑哪个 Run）**本来就是持久事件**，订阅时补一次就够了（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 4.2）。周期性再推一遍，就是把心跳变成第二条事件通道 —— 见第 4 节。

## 2. `manager` 与 `worker`

### 2.1 注册与心跳

`worker` 启动后连上任意一个 `manager` —— **报到就是第一次心跳**，只是多带了一样：**自己能跑什么**（沙箱镜像、工具运行时版本）。

之后按固定间隔发心跳，带三样：

- 活着
- **在跑哪些 Run、各自哪一步、这一步什么时候开始的**
- 还有多少空闲额度

**报到与心跳是同一个消息** —— 分开的话，重连之后会出现一个心跳周期的空窗，`manager` 以为没人跑（见 2.5）。

派发因此能挑负载最低的 `worker`，而不是随便扔。

**心跳里的是状态，不是事件** —— 见第 4 节。

### 2.2 派发与归属

`manager` 派发一个 Run 时：

- 在 `execution_runs` 上写一个**归属版本号（epoch）**，每次派发递增
- 把快照（Agent 的配置）与调用信息发给 `worker`

`worker` 不接受任何调度决策 —— 它只是收任务、跑、上报。

**epoch 是栅栏。** `manager` 看到连接断了，**区分不了"`worker` 死了"和"网络抖了一下"**：`worker` 可能还活着、还在跑、还在写日志。所以：

| | 管什么 |
|---|---|
| **连接** | **快** —— 断连是立刻可见的信号，不必等租约超时 |
| **epoch** | **对** —— 重投时 +1，旧 epoch 的 `worker` 再上报，日志写入被拒 |

连接的抖动因此最多浪费一次重投，**不会产生两条日志**。

### 2.3 事件上报

`worker` **先落库、再上报**：

1. 写 `execution_run_log`（它是这张表的唯一写者）
2. 再沿连接把事件推给 `manager`

**顺序不能反。** 反了的话，`manager` 推给客户端的事件可能比库里还新 —— 客户端一断线重连，反而拿到更旧的东西。

**粗粒度事件（`_call` / `_result`）落库；`message_delta` 不落库**，只沿连接转发（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 3.3）。

### 2.4 取消

`manager` 沿连接推一条取消，`worker` 在**步骤边界**检查。同时 `manager` 在库里落下持久的**取消标志** —— 连接断了取消仍要生效，推送只是让它更快。

### 2.5 重启与接管

**`manager` 重启后，内存里的注册表与连接表全没了** —— 于是它不知道哪些 Run 正在被跑。而 `worker` 会重连，**报到时带回「在跑哪些 Run」**（见 2.1），那份知识就回来了。

`manager` 周期性地扫 `execution_runs`：

> **非终态 ∧ 此刻没有任何 `worker` 声称在跑 ∧ 距上次派发超过 `T`** → 重新派发（`epoch` +1）

**`T` 就是重连的余量。** 它不能是「等连接建立完成」这个事件 —— `manager` 重启后不知道有几个 `worker` 会来报到。所以它只能是一个时间值，取大于「重连 + 报到」的量。

**取短了也不会错**：`worker` 报到了，判据第二条自动为假；没来得及报到就扫到，`epoch` 栅栏接住。

| | 管什么 |
|---|---|
| **`T`** | **少浪费** |
| **`epoch`** | **不错** |

和 2.2 那句是同一个形状。

**没有 `owner` 这一列** —— 单副本下没有别人可以归属。巡检的周期与 `T` 的取值见 [11-roadmap.md](./11-roadmap.md) 待定项 16。

## 3. `manager` 之间

### 3.1 为什么需要

`worker` 连在 `manager` A 上，订阅这个 Run 的客户端可能连在 `manager` B 上。而 **`message_delta` 不落库**，只存在于实时通道上 —— 所以 B 必须能从 A 拿到它。

### 3.2 路由

- 一张 `run → manager` 的**路由表**。它是 `worker` 注册表的投影：谁连着我、我在跑什么，反过来就是它
- 派发时写、`worker` 断开时清、`manager` 心跳保活
- B 订阅某个 Run 时先查它，再把订阅转给 A；A 把事件推过来
- 消息正在生成时，B 顺带向 A 要一份**当前累积文本**，用于重连补发（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 4.2）

### 3.3 一条必须守住的性质

> **路由失效只能导致"漏"，不能导致"错"。**

漏 = 那一段没有平滑文本，`llm_result` 会补齐 —— 可接受。错 = 串流 —— 数据事故。

陈旧的路由条目、A 挂掉后的空窗，都必须收敛到"这一段没有事件"。

### 3.4 规模

`manager` 全互联是 **N²**。池的粒度小的时候没问题，上限见 [11-roadmap.md](./11-roadmap.md) 待定项 14。

## 4. 状态与事件不是一回事

这是整份协议里最容易出错的一条。

| | 心跳里的状态 | 事件 |
|---|---|---|
| 载体 | 连接 | 连接 + 日志 |
| 保证 | **可丢、可过期** | 不可丢、可重放 |
| 用途 | 调度与运维 | 运行历史、对外推流 |
| 丢了会怎样 | 调度慢一拍 | 运行历史错误 |

**不能让心跳变成第二条事件通道。** 一旦 `manager` 图省事，拿心跳里的进度去给客户端推事件，重放路径和实时路径就不一致了 —— 而 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 4 节的全部价值，就在于这两条路径是同一条。

**客户端订阅时的那次补发不算例外** —— 它是从日志读出来的**一次性**补发，之后状态全由事件推进（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 4.2）。它和"周期性推状态"的区别，就在于是不是另有一条独立的来源。
