## 1. 连接

| 连接 | 方向 | 条数 | 承载 |
|---|---|---|---|
| `manager` ↔ 客户端 | 单向（服务端推） | 每个被订阅的会话一条 | 事件与状态。**只读**（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 4 节） |
| `manager` ↔ `worker`（常驻） | 双向 | 每个 `worker` 一条 | 下行：派发、取消。上行：报到与心跳 |
| `manager` ↔ `worker`（Run） | 双向 | 每个在跑的 Run 一条 | 上行：事件 |

**内部双向，外部单向** —— 所以两侧用不同的东西。客户端侧是 SSE（纯 HTTP，SDK 里不需要协议代码）；内部侧是自造的长连接协议。

**客户端侧的单位是会话，不是 Run。** 会话才是界面的单位，而且**空闲时也要有连接** —— 否则另一个标签页提交的 Run 推不进来。

**`worker` 侧有两条，是因为两件事的单位不同。** 报到与心跳是 **`worker` 级**的事实（能跑什么、能同时跑几个），一个 `worker` 只有一份；事件是 **Run 级**的，一个 Run 一串。混在一条上，一个 Run 的洪峰会推迟另一个 Run 的事件。

**常驻那条不能省。** 一个 Run 都没有的时候，`worker` 必须仍然在 `manager` 的视野里 —— 否则 `manager` 不知道下一个 Run 往哪派。它只报到一次，之后周期证明自己还在，**不承载任何 Run 状态**。

### 1.1 保活与心跳

**每条连接都「周期性地推一次状态」。** 它同时是**收敛点**（对上账）和**活着的证明** —— 所以没有另一套单独的保活机制。

| 连接 | 周期推什么 | 粒度 |
|---|---|---|
| 客户端 ↔ `manager` | **会话状态** | 会话级：空闲，还是正在跑某个 Run |
| `manager` ↔ `worker`（常驻） | **`worker` 还在** | `worker` 级 |
| `manager` ↔ `worker`（Run） | **这个 Run 跑到哪一步** | Run 级 |

间隔要**小于链路上最短的超时**（nginx 的 `proxy_read_timeout` 默认 60 秒，而一个慢步骤可能几十秒没有事件）。

**它也是活着的证明**：一端一段时间没收到任何消息就断开重连。**误判的代价只是重连一次** —— 游标是幂等的、重放不会错。这和 `epoch` 是同一个形状：**代价是浪费，不是错误。**

**能推什么是有边界的。** 判据是「它是不是事件的投影」—— 见第 4 节。

### 1.2 消息格式

**一条规则：处处都是 `{"type": "...", "data": {...}}`，`data` 永远是对象。**

内部侧在这之上加一层长度前缀，客户端那条把它放进 SSE 的 `data:` 行：

| | 内部 | 客户端 |
|---|---|---|
| 一帧 | `[4 字节长度][JSON]` | `id: <游标>` 换行 `data: <同一个 JSON>` |
| 解复用 | `type` | 同左 —— **不用 SSE 的 `event:`** |

**没有消息 id，也没有请求-响应。** 内部侧每条消息都是单向通知：派发和取消不期待回话，状态和事件也不需要。所以不需要消息 id，也不需要超时重传。

#### 类型的名字

**只有三种是这份协议定的**：`state` / `dispatch` / `cancel`。**其余一律是事件**：持久事件的名字直接来自日志类型（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 2 节）；流式事件以 `text_message_*` 为名（无日志类型，见同文 3.3）。线上名与 SDK 面同名，没有投影层。

**不认识一个名字该怎么办，取决于谁收到：**

| 哪条连接 | 收到不认识的名字 |
|---|---|
| 内部两条（`manager` ↔ `worker`） | **报错** —— 同一套部署一起升级，不认识就是 bug |
| 客户端那条 | **忽略** —— 客户端可能落后于平台，事件类型是开放的 |

这条区分落在**接收者**身上，不在字段层次上 —— 所以事件不必另起一层信封。

**协议的名字永不被事件占用。**

#### `state`

**三条连接各推各的，形状就是「这条连接此刻的状态」：**

```json
{"type": "state", "data": {"worker_id": "w_1"}}
```
```json
{"type": "state", "data": {"worker_id": "w_1", "run_id": "r_7f3a", "epoch": 3,
  "step": "tool:query_projects", "started_at": "2026-10-09T10:12:03Z"}}
```
```json
{"type": "state", "data": {"session_id": "s_91c4", "run": {"run_id": "r_7f3a", "seq": 7}}}
```

前两条是 `worker` 侧（常驻 / Run），第三条是客户端侧 —— **读的人只连自己那条**，形状不同不要紧；`worker` 侧的首次 `state` 多带几样（见 2.1）。

**客户端那条上的 `state` 由 `manager` 自己算出来** —— 它从内存缓存里读（见第 3 节），不是从 `worker` 转发的。

#### `dispatch` 与 `cancel`

**都走常驻连接** —— 取消可能比 Run 连接先到（Run 还没开跑），沿常驻推送得到。

```json
{"type": "dispatch", "data": {
  "run_id": "r_7f3a", "epoch": 3, "session_id": "s_91c4",
  "snapshot": {"…": "已发布的配置快照"},
  "input": {"…": "content / params / output_schema"}
}}
```
```json
{"type": "cancel", "data": {"run_id": "r_7f3a"}}
```

#### 事件

**直接用事件的类型** —— `type` 与 `data` 合起来就是日志表的一行（`created_at` 除外），不改名、不加前缀、也不另起一层：

```json
{"type": "tool_call", "data": {
  "run_id": "r_7f3a", "seq": 7, "action_id": "a_5b",
  "tool": "query_projects", "args": {}
}}
```

**事件因此是一串不变的字节** —— `manager` 从 `worker` 收到什么，就原样转发给订阅者，只多插一行 `id`。

**`id` 就是游标**：`<run_id>:<seq>`。**流式事件不带 `id`**，SSE 的语义会自动保持上一个不变 —— 正好就是「我停在哪儿」。

**流式事件还少两个字段** —— `seq` 和 `action_id` 都不带（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 3.3）。

## 2. `manager` 与 `worker`

### 2.1 注册与心跳

`worker` 启动后连上任意一个 `manager`，建**常驻连接** —— **报到就是第一次 `state`**，多带三样：**自己能跑什么**（沙箱镜像、工具运行时版本）、**能同时跑几个**、**手上还在跑哪些 Run**（`manager` 重启后靠它对账，见 2.5）。

之后按固定间隔发 `state`，只带一样：**还在**（连同 `worker_id`）。**"在跑哪些 Run"只在报到时报一次** —— 之后由 Run 连接的存续持续表达；空闲额度 = 声明的上限 − 当前连着的 Run 连接数，`manager` 自己减一下就得到。

**每个 Run 开始跑时，`worker` 再建一条 Run 连接**，它的第一条消息同样是一次 `state` —— 带 `run_id` 与 `epoch`，之后周期带上**跑到哪一步、这一步什么时候开始的**。

**报到与 `state` 是同一个消息** —— 分开的话，重连之后会出现一个周期的空窗，`manager` 以为没人跑（见 2.5）。

**周期推的是状态，不是事件** —— 见第 4 节。

### 2.2 派发与归属

`manager` 派发一个 Run 时：

- 在 `execution_runs` 上写一个**归属版本号（epoch）**，每次派发递增
- 沿**常驻连接**把快照（Agent 的配置）与调用信息推给 `worker`
- `worker` 收到后建一条 **Run 连接**，在那条上跑完这个 Run

**Run 连接的出现就是"开始跑了"的证据** —— 不需要另发一条确认。

`worker` 不接受任何调度决策 —— 它只是收任务、跑、上报。

**epoch 是栅栏。** `manager` 看到 Run 连接断了，**区分不了"`worker` 死了"和"网络抖了一下"**：`worker` 可能还活着、还在跑、还在写日志。所以：

| | 管什么 |
|---|---|
| **连接** | **快** —— 断连是立刻可见的信号，不必等租约超时 |
| **epoch** | **对** —— 重投时 +1，旧 epoch 的 `worker` 再写日志会被拒 |

**它防的不是「多跑一次」，是「日志写坏」。** `seq` 由 `worker` 自己分配 —— 两段执行同时往同一个 Run 写，就会出现**两组 `seq 1..N`**：客户端按 `seq` 去重会丢事件，续跑点也会判错。重投白跑一次只是浪费；这个不是。

### 2.3 事件上报

`worker` **先落库、再上报**：

1. 写 `execution_run_log`（它是这张表的唯一写者）
2. 再沿**这个 Run 的 Run 连接**把事件推给 `manager`

**顺序不能反。** 反了的话，`manager` 推给客户端的事件可能比库里还新 —— 客户端一断线重连，反而拿到更旧的东西。

**粗粒度事件（`_call` / `_result`）落库；`text_message_*` 不落库**，只沿 Run 连接转发（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 3.3）。

### 2.4 取消

`manager` 沿**常驻连接**推一条取消，`worker` 在**步骤边界**检查。同时 `manager` 在库里落下持久的**取消标志** —— 连接断了取消仍要生效，推送只是让它更快。

### 2.5 重启与接管

**`manager` 重启后，内存里的注册表与连接表全没了** —— 于是它不知道哪些 Run 正在被跑。

**巡检门控在连接建立之后**：

> `manager` 重启 → 等 `worker` 报到（带回「手上还在跑哪些 Run」）→ **才开始**周期巡检

**必须等这一步。** 巡检是拿连接表去比对的，而它要 `worker` 报到才完整。**单副本下这个门控是充分的** —— 一个 `worker` 连上就是全部。

之后周期性地扫 `execution_runs`：

> **非终态 ∧ 没有对应的 Run 连接 ∧ 不在 `worker` 报到时报的「还在跑哪些 Run」里 ∧ 不在「刚派发、还在等连接建立」里** → 重新派发（`epoch` +1）

**后两项是「连接表还不完整」的两个来源**，都要在内存里排除掉，否则巡检会自己把自己重派：一个是刚推出去的 `dispatch`（推完到 Run 连接建立有一个往返），一个是刚重连的 `worker`（它报了 N 个 Run，N 条连接还没建齐）。

**既不需要 `owner` 那一列，也不需要时间余量。** 单副本下没有别人可以归属；「连接表还不完整」那个窗口被门控直接消掉了。

巡检周期见 [11-roadmap.md](./11-roadmap.md) 待定项 15。**多副本下这个门控不成立** ——「第一个连上」不等于「都连上了」，见待定项 13。

## 3. `manager` 的内存缓存

**`manager` 记着正在跑的东西。** 它是**运行时态的投影，不是真相源** —— 丢了可以从日志与 `worker` 报到重建（见 2.5），所以不持久化，也不要求和日志强一致。

| 缓存项 | 谁刷新它 | 谁读它 |
|---|---|---|
| 活跃 Run 的**累积文本** | `event` 里的 `text_message_content` | 订阅时补发（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 4.2） |
| **跑到哪一步、什么时候开始的** | Run 连接的 `state` | 判死（见 [11-roadmap.md](./11-roadmap.md) 待定项 14） |
| **刚从报到里知道的「还在跑的 Run」** | 报到 | 巡检判据（见 2.5） |
| **刚派发、Run 连接还没建起来的 Run** | 派发 | 巡检判据（见 2.5） |

**刷新是无条件的** —— 不管有没有客户端连着，连接上来的消息都在刷。所以任何时候来一个订阅者，读到的都是一份现成的。

**它同时是周期推送的数据源**（见 1.1）：会话状态就是从「这个会话有没有活跃 Run」读出来的，一次内存查找。

**`manager` 重启会让它变空**，正在生成的那条消息的累积文本随之丢掉 —— **但这不致命**，它正好落在已经声明的保证里：内容不丢失，**增量粒度不保证**（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 4.3）。所以不需要为它加一条「向 `worker` 要累积文本」的协议。

## 4. 状态与事件不是一回事

这是整份协议里最容易出错的一条。

| | 状态推送 | 事件 |
|---|---|---|
| 载体 | 只有连接 | 连接 **+ 日志** |
| 保证 | **可丢、可过期** | 不可丢、可重放 |
| 丢了会怎样 | 下一次推就补上 | 运行历史就错了 |

**判据是「它是不是事件的投影」：**

| 推的内容 | 来源 | 能不能推给客户端 |
|---|---|---|
| 会话状态（空闲 / 在跑哪个 Run） | **事件的投影** —— 同一份数据 | **能** —— 推它就是复述，周期推就是收敛 |
| Run 连接的 `state` 里的「跑到哪一步、跑了多久」 | **不在事件流里** | **不能** —— 那是第二个来源 |

**第二行就是那条线。** `manager` 图省事拿它去给客户端推状态，重放路径和实时路径就分叉了 —— 而 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 4 节的全部价值，就在于这两条路径是同一条。

**Run 连接的 `state` 里带进度是对的**（判死要用，见 [11-roadmap.md](./11-roadmap.md) 待定项 14）—— **它是给 `manager` 看的，不是给界面看的。**
