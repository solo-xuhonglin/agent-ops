## 1. 两类连接

| 连接 | 方向 | 单位 | 承载 |
|---|---|---|---|
| `manager` ↔ 客户端 | 单向（服务端推） | **会话** | 事件与状态。**只读**（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 4 节） |
| `manager` ↔ `worker` | 双向 | **`worker`** | 下行：派发、取消。上行：心跳、状态、事件 |

**内部双向，外部单向** —— 所以两侧用不同的东西。客户端侧是 SSE（纯 HTTP，SDK 里不需要协议代码）；内部侧是自造的长连接协议。

**客户端侧的单位是会话，不是 Run。** 会话才是界面的单位，而且**空闲时也要有连接** —— 否则另一个标签页提交的 Run 推不进来。

**`manager` ↔ `worker` 的单位是 `worker`** —— 一个 worker 一条。报到与心跳是 worker 级的事实（能跑什么、还有多少空闲额度），按 Run 拆它们就没有落脚点。派发、取消、事件都带 `run_id`，在同一条上多路复用；同一个 Run 的事件天然保序，跨 Run 不需要保序。

### 1.1 保活与心跳

**两类连接都是「周期性地推一次状态」。** 它同时是**收敛点**（界面拿它对账）和**活着的证明** —— 所以没有另一套单独的保活机制。

| 连接 | 周期推什么 | 粒度 |
|---|---|---|
| 客户端 ↔ `manager` | **会话状态** | 会话级：空闲，还是正在跑某个 Run |
| `manager` ↔ `worker` | **`worker` 状态** | 一个 `worker` 上在跑哪些 Run |

间隔要**小于链路上最短的超时**（nginx 的 `proxy_read_timeout` 默认 60 秒，而一个慢步骤可能几十秒没有事件）。

**它也是活着的证明**：一端一段时间没收到任何消息就断开重连。**误判的代价只是重连一次** —— 游标是幂等的、重放不会错。这和 `epoch` 是同一个形状：**代价是浪费，不是错误。**

**能推什么是有边界的。** 判据是「它是不是事件的投影」—— 见第 4 节。

### 1.2 消息格式

**一条规则：处处都是 `{"type": "...", "data": {...}}`，`data` 永远是对象。**

内部那条连接在这之上加一层长度前缀，客户端那条把它放进 SSE 的 `data:` 行：

| | 内部 | 客户端 |
|---|---|---|
| 一帧 | `[4 字节长度][JSON]` | `id: <游标>` 换行 `data: <同一个 JSON>` |
| 解复用 | `type` | 同左 —— **不用 SSE 的 `event:`** |

**没有消息 id，也没有请求-响应。** 内部这条连接上每条消息都是单向通知：派发和取消不期待回话，心跳和事件也不需要。所以不需要消息 id，也不需要超时重传。

**两种「类型」，在两个层次上：**

| | 谁定的 | 开放性 | 收到不认识的 |
|---|---|---|---|
| 消息 `type` | 这份协议 | **封闭**，两侧同时改 | **报错** |
| `event_type` | [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 2 节，等于日志类型 | **开放** | **忽略** |

混在一层就说不清「不认识的该报错还是该忽略」。所以事件的类型不占 `type`，而是走一个带前缀的字段：

```json
{"type": "event", "data": {
  "run_id": "r_7f3a", "seq": 7, "action_id": "a_5b",
  "event_type": "tool_call",
  "event_data": {"tool": "query_projects", "args": {}}
}}
```

**`event_type` / `event_data` 就是日志表那一行的 `type` / `payload`**，上了线带前缀，免得和信封撞名。

**事件因此是一串不变的字节** —— `manager` 从 `worker` 收到什么，就原样转发给订阅者，只多插一行 `id`。

**`id` 就是游标**：`<run_id>:<seq>`。**流式事件不带 `id`**，SSE 的语义会自动保持上一个不变 —— 正好就是「我停在哪儿」。

**流式事件还少两个字段** —— `seq` 和 `action_id` 都不带（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 3.3）。

**其余四种消息：**

```json
{"type": "heartbeat", "data": {"runs": [
  {"run_id": "r_7f3a", "step": "tool:query_projects", "started_at": "2026-10-09T10:12:03Z"}
]}}
```
```json
{"type": "dispatch", "data": {
  "run_id": "r_7f3a", "epoch": 3, "session_id": "s_91c4",
  "snapshot": {"…": "已发布的配置快照"},
  "input": {"…": "content / params / output_schema"}
}}
```
```json
{"type": "cancel", "data": {"run_id": "r_7f3a"}}
```
```json
{"type": "session_state", "data": {"session_id": "s_91c4", "run": {"run_id": "r_7f3a", "seq": 7}}}
```

`heartbeat` 与 `event` 走 `worker` → `manager`，`dispatch` 与 `cancel` 走反向。**`session_state` 只在客户端那条连接上** —— 它是唯一一种不来自 `worker` 的消息，由 `manager` 从内存缓存里读出来（见第 3 节）。

## 2. `manager` 与 `worker`

### 2.1 注册与心跳

`worker` 启动后连上任意一个 `manager` —— **报到就是第一次心跳**，只是多带了一样：**自己能跑什么**（沙箱镜像、工具运行时版本）。

之后按固定间隔发心跳，带三样：

- 活着
- **在跑哪些 Run、各自哪一步、这一步什么时候开始的**
- 还有多少空闲额度

**报到与心跳是同一个消息** —— 分开的话，重连之后会出现一个心跳周期的空窗，`manager` 以为没人跑（见 2.5）。

**心跳里的是状态，不是事件** —— 见第 4 节。

### 2.2 派发与归属

`manager` 派发一个 Run 时：

- 在 `execution_runs` 上写一个**归属版本号（epoch）**，每次派发递增
- 把快照（Agent 的配置）与调用信息发给 `worker`

`worker` 不接受任何调度决策 —— 它只是收任务、跑、上报。

**epoch 是栅栏。** `manager` 看到连接断了，**区分不了"`worker` 死了"和"网络抖了一下"**：`worker` 可能还活着、还在跑、还在写日志。所以：

| | 管什么 |
|---|---|
| **连接** | **快** —— 断连是立刻可见的信号，不必等租约超时 |
| **epoch** | **对** —— 重投时 +1，旧 epoch 的 `worker` 再写日志会被拒 |

**它防的不是「多跑一次」，是「日志写坏」。** `seq` 由 `worker` 自己分配 —— 两段执行同时往同一个 Run 写，就会出现**两组 `seq 1..N`**：客户端按 `seq` 去重会丢事件，续跑点也会判错。重投白跑一次只是浪费；这个不是。

### 2.3 事件上报

`worker` **先落库、再上报**：

1. 写 `execution_run_log`（它是这张表的唯一写者）
2. 再沿连接把事件推给 `manager`

**顺序不能反。** 反了的话，`manager` 推给客户端的事件可能比库里还新 —— 客户端一断线重连，反而拿到更旧的东西。

**粗粒度事件（`_call` / `_result`）落库；`message_delta` 不落库**，只沿连接转发（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 3.3）。

### 2.4 取消

`manager` 沿连接推一条取消，`worker` 在**步骤边界**检查。同时 `manager` 在库里落下持久的**取消标志** —— 连接断了取消仍要生效，推送只是让它更快。

### 2.5 重启与接管

**`manager` 重启后，内存里的注册表与连接表全没了** —— 于是它不知道哪些 Run 正在被跑。

**巡检门控在连接建立之后**：

> `manager` 重启 → 等 `worker` 连上 → `worker` 报到（带回「在跑哪些 Run」）→ **才开始**周期巡检

**必须等这一步。** 巡检是拿连接表去比对的，而它要 `worker` 报到才完整。**单副本下这个门控是充分的** —— 一个 `worker` 连上就是全部。

之后周期性地扫 `execution_runs`：

> **非终态 ∧ 不在 `worker` 报的「在跑哪些 Run」里 ∧ 不在「刚派发、还在等上报」里** → 重新派发（`epoch` +1）

第三条是内存里的一个小集合 —— 派发到 `worker` 报上来之间有一个心跳间隔，不排除它就会自己把自己重派。

**既不需要 `owner` 那一列，也不需要时间余量。** 单副本下没有别人可以归属；「连接表还不完整」那个窗口被门控直接消掉了。

巡检周期见 [11-roadmap.md](./11-roadmap.md) 待定项 16。**多副本下这个门控不成立** ——「第一个连上」不等于「都连上了」，见待定项 14。

## 3. `manager` 的内存缓存

**`manager` 记着正在跑的东西。** 它是**运行时态的投影，不是真相源** —— 丢了可以从日志与 `worker` 报到重建（见 2.5），所以不持久化，也不要求和日志强一致。

| 缓存项 | 谁刷新它 | 谁读它 |
|---|---|---|
| 活跃 Run 的**累积文本** | `event` 里的 `message_delta` | 订阅时补发（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 4.2） |
| **跑到哪一步、什么时候开始的** | `heartbeat` | 判死（见 [11-roadmap.md](./11-roadmap.md) 待定项 15） |
| **刚派发、还没被上报确认的 Run** | 派发 / `heartbeat` | 巡检判据（见 2.5） |

**刷新是无条件的** —— 不管有没有客户端连着，连接上来的消息都在刷。所以任何时候来一个订阅者，读到的都是一份现成的。

**它同时是周期推送的数据源**（见 1.1）：会话状态就是从「这个会话有没有活跃 Run」读出来的，一次内存查找。

**`manager` 重启会让它变空**，正在生成的那条消息的累积文本随之丢掉 —— **但这不致命**，它正好落在已经声明的保证里：内容不丢失，**增量粒度不保证**（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 4.3）。所以不需要为它加一条「向 `worker` 要累积文本」的协议。

## 4. 状态与事件不是一回事

这是整份协议里最容易出错的一条。

| | 状态推送 | 事件 |
|---|---|---|
| 载体 | 只有连接 | 连接 **+ 日志** |
| 保证 | **可丢、可过期** | 不可丢、可重放 |
| 丢了会怎样 | 下一次推就补上 | 运行历史就错了 |

**判据是「它是不是事件的投影」：**

| 推的内容 | 来源 | 能不能推给客户端 |
|---|---|---|
| 会话状态（空闲 / 在跑哪个 Run） | **事件的投影** —— 同一份数据 | **能** —— 推它就是复述，周期推就是收敛 |
| `worker` 心跳里的「跑到哪一步、跑了多久」 | **不在事件流里** | **不能** —— 那是第二个来源 |

**第二行就是那条线。** `manager` 图省事拿它去给客户端推状态，重放路径和实时路径就分叉了 —— 而 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 4 节的全部价值，就在于这两条路径是同一条。

**`worker` 心跳里带进度是对的**（判死要用，见 [11-roadmap.md](./11-roadmap.md) 待定项 15）—— **它是给 `manager` 看的，不是给界面看的。**
