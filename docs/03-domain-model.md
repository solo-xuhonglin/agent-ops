## 1. 划分依据

模型按**领域**组织，不按技术分层。

划分依据是**变更原因与所有权**：同一个领域里的表，因为同样的理由被改动、被同一批人关心。

**检验方法只有一条：它们会不会在同一次编辑里一起改？**

- **会** → 同一个领域。例：Agent 的定义、编排、挂载、子 Agent 引用 —— 同一个人、同一个配置界面、同一次保存。
- **不会** → 不同领域。例：工具和 Skill —— 外部接口变了改工具，知识过时了改 Skill。

**不能用"减少跨域引用"作为合并领域的理由。** 那是技术诉求，不是变更驱动 —— 拿它划分领域，等于让持久化层的方便程度决定业务边界。

### 1.1 依赖图

八个领域，依赖方向**必须无环**：

```
       ┌──→ tool ──────┐
       │               │
iam ───┼──→ skill ─────┼──→ agent ──→ release ──→ execution
       │               │                              │
       └──→ secrets ───┘                              │
              ↑                                      │
              └──────────────────────────────────────┘

audit ← 被所有领域写入，不反向依赖任何领域
```

`tool` / `skill` / `secrets` 是**并列的兄弟**，互不依赖 —— 它们都只依赖 `iam`，都被 `agent` 依赖。

`execution` 有**两条出边**：`release` 给它配置，`secrets` 给它凭据。凭据不进快照（见第 3 节），所以它必须单独读活的。

### 1.2 八个领域

| 领域 | 聚合根 | 装什么 | 变更驱动 |
|---|---|---|---|
| `iam` | Tenant | 租户（= 外部团队）、账号、成员、邀请、配额、用量 | 团队的组织与调整 |
| `tool` | Tool | 工具定义 | 外部接口变化 |
| `skill` | Skill | Skill 定义 | 领域知识更新 |
| `secrets` | Credential | 外部系统的账号凭据 | 外部账号的变更与轮换 |
| `agent` | Agent | 定义、编排、挂载、子 Agent、调用 key、上下文策略 | 产品能力与流程 |
| `release` | Artifact | 草稿 → 版本 → 发布 → 回滚 | 发布策略 |
| `execution` | 会话 / 运行 | 会话、运行、运行日志 | 引擎演进 |
| `audit` | AuditEntry | 变更审计，只追加 | 合规要求 |

**命名原则：前缀描述事物，不描述活动。** 领域名一律用名词（`agent` / `release`），不用动名词 —— 前者一眼知道里面装什么，后者只说明这里在干什么。

**表名是 `<领域>_<实体>`。域名与聚合根同名时加后缀消歧** —— `agent_definitions`、`tool_definitions`，因为 `agent_agents` / `tool_tools` 不可读。

## 2. 边界的关键判断

### 2.1 `release` 独立于所有可发布物

版本与发布有自己的语言（草稿 / 发布 / 回滚 / changelog）和不变式（版本单调、发布不可变），并且**泛化于所有可发布物** —— v1 的可发布物是 Agent / Tool / Skill，将来可能有 Prompt / Dataset / Eval。

由它持有版本表，各领域不各自造一套。

**快照只含配置。** 序列化的是定义本身 —— 编排结构、能力挂载、子 Agent 引用，以及挂载到的 Tool / Skill 的**版本号**。**不含**调用 key、责任人、归档标志这些会独立变化的东西。

> 这条边界是硬的：**快照若连 key 一起冻结，回滚一个旧版本就会把所有已交付的后端调用方一起打断。**

### 2.2 `audit` 独立于 `iam`

两者的变更驱动不同（合规要求 vs 组织调整），且审计被**所有**领域写入。塞进一个笼统的"治理"领域，只会让边界说不清。

**`audit` 是「每张表只有一个写者」的唯一例外** —— 它按设计就是多写者，各领域写自己的变更记录，只追加、不修改。除此之外每张表仍然只有一个写者。

**执行域横跨两个服务，但按表分得干净。** 会话与提交信息（`execution_sessions` / `execution_runs`）是结构性字段，由 `manager` 写；运行日志（`execution_run_log`）是执行模型本身，由 `worker` 写 —— **每张表仍然只有一个写者**。见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 1 节。

### 2.3 `tool` 与 `skill` 是两个领域

除了"都给 Agent 用"之外，它们没有任何共同点 —— 而那是**关系**，不是**本质**：

| | `tool` | `skill` |
|---|---|---|
| 是什么 | 能执行的东西 | 要读的知识 |
| 机制 | 沙箱执行 / HTTP 调用 | 文本注入上下文 |
| 变更驱动 | 外部接口变了 | 知识更新了 |
| 不变式 | schema 合法、有入口 | 必须有 description |

`secrets` 是第三个兄弟：外部账号的凭据。它的变更驱动是**外部账号的变更与轮换**，与前两者都没有交集。

### 2.4 `agent` 收拢六样东西

Agent 的定义、编排结构、能力挂载、子 Agent 引用、调用 key、上下文策略 —— **六样，一个领域**。

依据是第 1 节那条检验：它们在同一次编辑里一起改。编排结构（节点、边）与挂载关系是 Agent 聚合的**值对象**，不是独立实体。

### 2.5 `iam` 装的是一个团队在平台上的一切

**租户就是外部团队。** 一个团队接进来，它需要的身份与额度全在 `iam` 里：

| | 装什么 | 判权路径 |
|---|---|---|
| 成员 | 能用配置 UI 的人 | 配置权，按角色 |
| 配额与用量 | 这个团队用了多少 | — |
| 邀请 | 加入团队的唯一入口 | — |

**配额与用量 v1 只建不用** —— 模型落在 `iam`，但判定链不卡它（见 [10-permissions.md](./10-permissions.md) 2.2）。

**放一个领域，是因为它们同属一个主体** —— 都是团队自己的东西，不属于"平台"和"外部"两侧。

**没有"应用"这一层实体。** 外部程序调用 Agent 用 **Agent 自己的 key**，中间不需要一个实体来持有凭据（见 [10-permissions.md](./10-permissions.md) 第 2 节）。少一层概念，也少一张授权表。

> **仍然不打通的是另一件事**：调用时传进来的**终端用户标识**不是团队成员，也不参与判权。平台不做单点登录，也不信任外部用户目录。

### 2.6 账号是平台级的，成员关系是租户级的

**「账号」与「在某团队里是谁」是两件事。**

| | 级别 | 装什么 |
|---|---|---|
| 账号 | 平台 | 邮箱与口令。**邮箱全平台唯一** |
| 成员关系 | 租户 | 某个账号在某个团队里的角色 |
| 邀请 | 租户 | 把账号与团队连起来的**唯一入口** |

**同一个人可以同时属于多个团队**，登录后切换当前团队。

**加入团队必须靠邀请。** 开放注册后自由选团队，等于谁都能进任何团队。

> **开租户不是产品功能。** 租户由平台运营方手工开（运维动作），v1 不做自助开户 —— 因此平台侧不需要一个"运营方"角色。

### 2.7 运行不引用定义，只引用版本

一份定义可以开出多个会话、多次运行 —— 那属于 `execution`。而且执行域**只引用发布版本，不引用定义本身**。

**运行只认已发布的版本。** 这比单纯的"定义 / 实例"分家更严：每一次运行都能精确复现。

**唯一的例外是凭据** —— 它不进快照，运行时读活的那一份。这是刻意的：换一份凭据不该需要重新发布 Agent。

## 3. 依赖方向规则

跨领域引用**只允许沿依赖方向**，即由右向左：

| 引用方 | 被引用 | 说明 |
|---|---|---|
| `agent` | `iam` | 责任人是团队成员 |
| `agent` | `tool` | 挂载 |
| `agent` | `skill` | 挂载 |
| `agent` | `secrets` | 挂载工具时提供凭据 |
| `release` | `agent` / `tool` / `skill` | 多态引用 —— **版本化的是谁** |
| `release` | `secrets` | 只引用，**不版本化** —— 快照记的是"用哪一份" |
| `execution` | `release` | 运行绑定版本 |
| `execution` | `secrets` | 运行时取用**活**凭据 |

**凭据只被引用，不被版本化。** 换一份凭据、改一个口令，都不需要重新发布 Agent。

**反向引用一律不允许。** 例：`tool` 不可引用 `agent` —— 工具不知道谁在用它，这是刻意的。

`audit` 是**汇点**：所有领域都写它，它不引用任何领域。

**`tenant_id` 不在上表里。** 它是租户隔离列，出现在每个领域表上，指向 `iam.tenants`，由请求的租户上下文统一保证，不逐条校验。

## 4. 实现约定

1. **领域边界用表名前缀表达，不用数据库 schema。** 领域边界是应用层概念，不是数据库对象边界。单 schema 让迁移、备份、跨领域查询都保持简单。
2. **不使用数据库外键，引用完整性由应用层在事务内保证。** 代价是完整性从数据库强制降为程序强制，且失去级联删除与类型安全引用。**必须补齐引用清单、写入前校验、删除规则、孤儿巡检、导入路径五道防线** —— 那是强制要求，不是建议。
3. **跨领域引用只能多态表达。** 用 `(种类, id)` 而非具体外键列 —— 领域之间本来就不该有强耦合的引用。
4. **除执行域与审计域外一律软删除。** 实体删除 = 归档，行保留。这同时消除了大部分悬空引用风险。
5. **权限全部由程序实现。** 数据库只有一个应用账号，对所有表有完整权限，判定发生在应用层 —— 不使用数据库的 `GRANT` / `REVOKE`。
6. **没有共享父表。** 每个领域的实体自己持有身份与并发控制；跨领域的统一列表走读模型（CQRS 投影），投影可随时从领域表重建。

## 5. 未来领域的接入点

v1 不做的领域，将来加回时的位置：

- **模型目录（`model_`）**：独立领域，被 `agent` 依赖。把模型标识从 Agent 定义与节点上抽走，换成引用；单价表、配额、路由策略随之落地。
