## 1. 运行日志是唯一真相源

`execution_run_log`，**只追加**，一行一个事实。`runtime` 是它唯一的写者。

| 列 | |
|---|---|
| `run_id` | |
| `seq` | 在这个 Run 内从 1 单调递增，**由持有该 Run 的 worker 分配** |
| `action_id` | 动作身份。`_call` 分配，**重试复用**（见第 5 节） |
| `type` | 见第 2 节 |
| `payload` | JSONB |
| `created_at` | |

**Run 的状态就是这串日志的尾部。** `run.status` 列只是它的缓存投影，好让 `get_run` 一次查询拿到 —— 不是第二份真相。

**日志同时就是 trace。** 每一步的输入、输出、tokens、成本、耗时都在 `payload` 里，没有另一张 trace 表 —— 回放、观测、续跑读的是同一份数据，也不引入独立的 trace 系统。

## 2. 记什么：类型就是编排的动作词汇表

[04-orchestration.md](./04-orchestration.md) 2.1 说节点四种 —— LLM 调用、工具调用、子 Agent、条件分支。两种编排模式编译成同一张图，所以**只有一套词汇表能同时装下 ReAct 的一轮和 DAG 的一个节点**。

| `type` | payload |
|---|---|
| `run_started` | 输入、会话、调用方与终端用户标识 |
| `llm_call` | 送进模型的完整消息 |
| `llm_result` | 输出的消息、tokens、成本、耗时 |
| `tool_call` | 工具名、参数（**凭据注入前**）、幂等键 |
| `tool_result` | 结果或错误、耗时 |
| `agent_call` | 子 Agent、它的输入 |
| `agent_result` | 子 Agent 的输出 |
| `branch_taken` | 判定结果与走向 |
| `run_finished` / `run_failed` | 终态、结果或错误 |

**配对不变式**：每个动作是一对 `_call` / `_result`，靠 `action_id` 关联 —— **不依赖严格交替**（ReAct 一轮可以并发调多个工具，顺序会交错）。

「有一条 `_call` 没有配对的 `_result`」是**「这一步没跑完」的唯一判据** —— 续跑点、重试对象、崩溃残迹，三种问题一个查询。

**`_call` 的 payload 必须带这一步的输入。** 工具步骤记下工具名与参数，LLM 步骤记下送进去的消息。**于是重投不需要模型重新决策** —— 未完成的那一步，参数原样躺在日志里，照着重发即可。这既让续跑确定，也让 `action_id` 在重试前后保持稳定，幂等键才立得住。

## 3. 对外事件

**事件类型与日志类型一一对应**，中间不做抽象层。事件流的消费者是程序 —— 业务后端、业务前端的 JS。终端用户看到什么由那层程序决定；平台把它抽象成「思考中 / 执行中」，业务前端想显示「正在查询订单」就拿不到了。

事件分两类，区别只在于**能不能重放**：

| | 带序号 | 落库 | 可重放 | 客户端 |
|---|---|---|---|---|
| **持久事件** | ✅ | ✅ | ✅ | 按序号去重后应用 |
| **流式事件** | ❌ | ❌ | ❌ | 直接应用，不参与去重 |

**持久事件**与日志一一对应：

| 事件 | 带什么 | 不带什么 |
|---|---|---|
| `run_started` | 输入、会话 | 版本、编排方式 |
| `llm_call` | 动作 id | 输入消息 |
| `llm_result` | 输出消息、tokens、成本、耗时 | 模型名与参数 |
| `tool_call` | 工具名、参数、动作 id | |
| `tool_result` | 结果或错误、耗时、动作 id | |
| `agent_call` / `agent_result` | 子 Agent 名 / 输出 | 子 Agent 的输入、子运行的内部事件 |
| `branch_taken` | 分支标签 | 节点 id、边、图的形状 |
| `run_finished` / `run_failed` | 终态、结果或错误 | |

**流式事件**只有两个，它们是「一条消息正在生成」时的形状：

| 事件 | 语义 |
|---|---|
| `message_started` | **一条新消息开始 —— 客户端清空当前消息缓冲** |
| `message_delta` | 追加文本 |

**`message_started` 为什么单独存在、且不带序号**：断线补发与步骤重试都必须重新发出它，而带序号的重置信号会被客户端的去重逻辑丢掉。重试因此自然会让客户端清空缓冲，两次尝试的文本不会叠在一起。

### 3.1 引用外发，内容不外发

- **工具名、分支标签、子 Agent 名** —— 指向配置的**引用**，租户自己起的名字，外发
- **System Prompt 全文、Skill 正文、凭据、模型参数、节点 id 与图的形状** —— 配置的**内容**，不外发

于是 `llm_call` 不带输入消息（那里面装着 System Prompt 与 Skill 正文），而 `tool_call` 带参数（参数是这次运行生成的数据，不是配置）。

**凭据不留口子。** 日志记的是**注入前、带占位符**的参数 —— 凭据在真正发请求时才注入。所以 `tool_call` 外发在凭据上是安全的，也守住了「明文不进运行日志」（见 [08-credentials.md](./08-credentials.md) 第 4 节）。

### 3.2 未知类型必须忽略

契约要求调用方忽略不认识的事件类型。有了这一条，平台加一种动作类型就是纯增量，不构成兼容性变更。

### 3.3 流式事件为什么不落库

它们是**平滑度**，不是**内容** —— 内容完整地存在于 `llm_result` 的 payload 里。

代价明说：断线期间的文本增量不会重放，重连后可能「等这一步结束，一次性拿到整段文本」。**内容不丢失，增量粒度不保证。**

## 4. 推流与断线重连

### 4.1 传输

**SSE。** 它原生支持 `Last-Event-ID` —— 断线自动重连时浏览器自动带上最后收到的 id，与 `stream(from_seq=n)` 是同一件事。重连游标语义是协议内置的，不需要另造一套。

### 4.2 一次订阅做三件事

`gateway` **无状态**，任何副本都能接任何 `stream`：

1. 从 `execution_run_log` 读 `seq > from_seq` 的**持久事件**，按序推
2. 若此刻有消息正在生成，先推一条 `message_started`，再把当前累积文本作为一条 `message_delta` 推出去
3. 接上实时通道，按 `seq` 去重

没有第 2 步，客户端会丢掉一个**正在进行中、尚未结束**的消息 —— 它既不完整也不可恢复。Redis 里留一份 `run:{id}:live` 的当前消息快照（短 TTL）供这一步取用。

### 4.3 保证

| | |
|---|---|
| 内容 | **不丢失** —— `llm_result` 兜底 |
| 增量粒度 | **不保证** —— 断线期间的文本增量不重放 |
| 持久事件 | 序号单调递增；可能重复，调用方按 `seq` 去重 |
| 流式事件 | 不带序号，直接应用 |

### 4.4 超出重放窗口

日志的保留期**就是**重放窗口。`from_seq` 落在窗口之外时**明确报错** —— 不静默从当前位置开始，那会让调用方以为消息连续，实际中间缺了一段。

### 4.5 多订阅者

同一个 Run 允许被多个客户端同时 `stream`，互不影响。

**推流是无状态的广播** —— 事件从日志来、从 Redis 频道来，N 个订阅者看到同一串事件，彼此不可见。每个连接有自己的游标（`from_seq`）和消息缓冲，各自在自己的 `message_started` 上重置。

**冲突全部发生在会话的写上，不在推流上** —— 见第 7 节。

实现上，每个 `gateway` 副本为**每个正在被观看的 Run** 维护一个 tailer（读日志 + 订阅频道），再广播给连在它这台的订阅者。副本之间互不知晓，也不需要知晓。

## 5. Worker 与重投

**一个 Run 在同一时刻只有一个 worker**，由队列与租约保证。

**崩溃后重投**：新 worker 读日志重建状态 —— 依已完成的步骤恢复**会话上下文**（会话状态外置，见 [01-agent-platform-design.md](./01-agent-platform-design.md) 2.2）—— **从第一个没有 `_result` 的 `_call` 接着跑**。

**语义是 at-least-once。** 跑了一半的那一步会被重试：

- LLM 步骤重试无害
- **工具步骤可能重复副作用** —— 所以每个工具调用带上确定性**幂等键 `run_id + action_id`**（请求头），外部系统愿意配合就能去重

**不藏这条**：外部系统不支持幂等键时，重复副作用是真会发生的。这是 at-least-once 的定义，不是缺陷。

**重试有上限**，超了把 Run 判 `failed`。取值见 [10-roadmap.md](./10-roadmap.md) 待定项 12。

重试时重新写一行 `_call`：**`seq` 是新的，`action_id` 不变**。客户端因此收到一次新的 `message_started`，自然清空缓冲；幂等键也保持不变。

## 6. 取消

`cancel()` 是**请求**，不是动作：

- `gateway` 只读、写不了，所以取消请求转给 `runtime`，由它落一个持久的**取消标志**
- worker 在**步骤边界**检查这个标志
- 正在飞的 LLM 调用能中断就中断，不能就在它结束后停
- **已经发出去的工具调用不撤回** —— 副作用留在那边
- 终态 `cancelled` 由 **worker 自己**追加一行日志 —— 不能让 `runtime` 直接写，否则日志里会出现"已取消"后面还跟着 `tool_result`

`cancel()` **立即返回，不阻塞** —— 一次在飞的 LLM 调用可能几十秒。终态通过 `wait()` / `stream()` 观察。

## 7. 会话

**会话是单主体的：一个会话 = 一个调用主体的一段连续上下文。** 两个终端用户不会落进同一个会话，后端也不会把多个用户塞进一个会话。

主体是**创建它的那把 key 背后的人**：

| 提交方 | 主体 |
|---|---|
| 前端（临时 key） | 那个终端用户 —— 临时 key 上绑着 |
| 后端（永久 key） | 调用方本身 |

后端的主要场景是**定时任务**，而定时任务大多不传 `session`、不建会话 —— 所以实践里会话几乎全是前端的。

**主体只标归属与审计，不判权。** 它和 Agent 的责任人同一定位：标明这段对话是谁的，不含权限含义（见 [09-permissions.md](./09-permissions.md) 2.3）。

### 7.1 一个会话同一时刻只有一个活跃 Run

会话是一份共享的可变消息历史。两个 Run 并发跑，各自读到同一份历史、各自追加 —— 结果是交错或丢更新。

所以会话上有一个**活跃 Run 租约**：提交时抢占，占着就拒绝。客户端在运行中禁用发送键，**服务端的拒绝是兜底**。

**拒绝而不是排队**：第二句话是**对着旧上下文写的**。排队执行时上下文已经变过一次，产出的历史解释不通。

会话因此**不只是 Run 的容器** —— 它有一条要在事务里抢占的不变式、一个主体、一段独立于 Run 的生命周期。它是自己的聚合，Run 是它的子项（见 [03-domain-model.md](./03-domain-model.md) 1.2）。
