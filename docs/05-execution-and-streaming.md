## 1. 运行日志是唯一真相源

执行域三张表，**每张表只有一个写者**：

| 表 | 装什么 | 写者 |
|---|---|---|
| `execution_sessions` | 会话、活跃 Run 租约 | `manager` |
| `execution_runs` | 提交信息、派发归属（epoch） | `manager` |
| `execution_run_log` | 运行日志 | `worker` |

`execution_run_log` **只追加**，一行一个事实：

| 列 | |
|---|---|
| `run_id` | |
| `seq` | 在这个 Run 内从 1 单调递增，**由持有该 Run 的 `worker` 分配** |
| `action_id` | 动作身份。`_call` 分配，**重试复用**（见第 5 节） |
| `type` | 见第 2 节 |
| `payload` | JSONB |
| `created_at` | |

**拆在这个位置是一条硬边界。** 前两张是结构性的、可穷举的字段 —— 会话、提交、归属。**提交必须同步拿到一个持久的 id**（见 [02-sdk-contract.md](./02-sdk-contract.md) 第 3 节），而那一刻还没有 `worker`，所以只能由 `manager` 写。

`execution_run_log` 装的是**类型与载荷**，也就是执行模型本身 —— 它会随编排方式变。写者放在 `worker`，领域模型因此仍然只有一份定义（`shared/`，见 [01-agent-platform-design.md](./01-agent-platform-design.md) 第 4 节）。

**Run 的状态就是这串日志的尾部**，不另存一列 —— 存了就会出现"`manager` 写 `pending`、`worker` 改 `running`"这种同一列两个写者。

**日志同时就是 trace。** 每一步的输入、输出、tokens、成本、耗时都在 `payload` 里，没有另一张 trace 表 —— 回放、观测、续跑读的是同一份数据。

## 2. 记什么：类型就是运行的词汇表

[04-orchestration.md](./04-orchestration.md) 2.1 说节点四种 —— LLM 调用、工具调用、子 Agent、条件分支。两种编排模式编译成同一张图，所以**只有一套词汇表能同时装下 ReAct 的一轮和 DAG 的一个节点**。

| `type` | payload |
|---|---|
| `run_started` | 输入、会话、调用方与终端用户标识 |
| `llm_call` | 送进模型的完整消息 |
| `llm_result` | 输出的消息、tokens、成本、耗时 |
| `tool_call` | 工具名、参数（**凭据注入前**）、幂等键 |
| `tool_result` | 结果或错误、耗时 |
| `agent_call` | 子 Agent、它的输入 |
| `agent_result` | 子 Agent 的输出 |
| `branch_taken` | 判定结果与走向 |
| `context_compacted` | 压缩前后的长度、被压掉的动作范围、摘要全文、tokens 与成本 |
| `run_finished` / `run_failed` | 终态、结果或错误 |

**`context_compacted` 是唯一不成对的类型** —— 它不发起一个动作，它报告一件引擎已经做完的事（见第 8 节）。它仍在同一串日志里，因为它同样是「运行中发生的事」，同样要能重放、要能按 `seq` 排序。

**配对不变式**：每个动作是一对 `_call` / `_result`，靠 `action_id` 关联 —— **不依赖严格交替**（ReAct 一轮可以并发调多个工具，顺序会交错）。

「有一条 `_call` 没有配对的 `_result`」是**「这一步没跑完」的唯一判据** —— 续跑点、重试对象、崩溃残迹，三种问题一个查询。

**`_call` 的 payload 必须带这一步的输入。** 工具步骤记下工具名与参数，LLM 步骤记下送进去的消息。**于是重投不需要模型重新决策** —— 未完成的那一步，参数原样躺在日志里，照着重发即可。这既让续跑确定，也让 `action_id` 在重试前后保持稳定，幂等键才立得住。

## 3. 对外事件

**事件类型与日志类型一一对应**，中间不做抽象层。事件流的消费者是程序 —— 业务后端、业务前端的 JS。终端用户看到什么由那层程序决定；平台把它抽象成「思考中 / 执行中」，业务前端想显示「正在查询订单」就拿不到了。

事件分两类，区别只在于**能不能重放**：

| | 带序号 | 落库 | 可重放 | 客户端 |
|---|---|---|---|---|
| **持久事件** | ✅ | ✅ | ✅ | 按序号去重后应用 |
| **流式事件** | ❌ | ❌ | ❌ | 直接应用，不参与去重 |

**持久事件**与日志一一对应：

| 事件 | 带什么 | 不带什么 |
|---|---|---|
| `run_started` | 输入、会话 | 版本、编排方式 |
| `llm_call` | 动作 id | 输入消息 |
| `llm_result` | 输出消息、tokens、成本、耗时 | 模型名与参数 |
| `tool_call` | 工具名、参数、动作 id | |
| `tool_result` | 结果或错误、耗时、动作 id | |
| `agent_call` / `agent_result` | 子 Agent 名 / 输出 | 子 Agent 的输入、子运行的内部事件 |
| `branch_taken` | 分支标签 | 节点 id、边、图的形状 |
| `run_finished` / `run_failed` | 终态、结果或错误 | |

**流式事件**只有两个，它们是「一条消息正在生成」时的形状：

| 事件 | 语义 |
|---|---|
| `message_started` | **一条新消息开始 —— 客户端清空当前消息缓冲** |
| `message_delta` | 追加文本 |

**`message_started` 不带序号** —— 断线补发与步骤重试都要重新发出它，带序号的重置信号会被客户端的去重丢掉。

### 3.1 引用外发，内容不外发

- **工具名、分支标签、子 Agent 名** —— 指向配置的**引用**，租户自己起的名字，外发
- **System Prompt 全文、Skill 正文、凭据、模型参数、节点 id 与图的形状** —— 配置的**内容**，不外发
- **调用方给的 `params`** —— 这次运行的数据，外发。它进的是**用户消息**，不进指令面，判据与渲染见 [02-sdk-contract.md](./02-sdk-contract.md) 第 4 节

于是 `llm_call` 不带输入消息（那里面装着 System Prompt 与 Skill 正文），而 `tool_call` 带参数（参数是这次运行生成的数据，不是配置）。

**凭据不留口子。** 日志记的是**注入前、带占位符**的参数 —— 凭据在真正发请求时才注入。所以 `tool_call` 外发在凭据上是安全的，也守住了「明文不进运行日志」（见 [09-credentials.md](./09-credentials.md) 第 4 节）。

### 3.2 未知类型必须忽略

契约要求调用方忽略不认识的事件类型。有了这一条，平台加一种动作类型就是纯增量，不构成兼容性变更。

### 3.3 流式事件不落库

它们是**平滑度**，不是**内容** —— 内容完整地存在于 `llm_result` 的 payload 里。

代价明说：断线期间的文本增量不会重放，重连后可能「等这一步结束，一次性拿到整段文本」。**内容不丢失，增量粒度不保证。**

## 4. 推流与断线重连

### 4.1 传输

**SSE over `fetch`。** 不用原生 `EventSource` —— 它设不了自定义请求头，key 只能塞进 URL，而 URL 会进日志和 referrer。用 `fetch` 流式读：key 走请求头，重连由 SDK 自己做（`from_seq` 本来就是我们的语义）。

客户端连接是**单向只读**的。`submit` / `cancel` / `get_run` 是请求-响应，走普通 HTTP —— 把控制动作塞进长连接，等于自己实现一遍请求-响应。保持只读有个很大的好处：**这条连接断了、重连了、换了副本，都不需要和任何状态对账。**

### 4.2 一次订阅做四件事

`manager` 的连接表是**软状态**，任何副本都能接任何 `stream`：

1. 从 `execution_run_log` 读 `seq > from_seq` 的**持久事件**，按序推
2. 查路由表，把订阅转给**持有该 Run 的 `manager`**（见 [06-internal-protocol.md](./06-internal-protocol.md) 第 3 节）
3. 若此刻有消息正在生成，向那边要一份**当前累积文本**，推一条 `message_started` 加一条 `message_delta` —— 客户端据此清空缓冲、重新累积
4. 接上实时通道，按 `seq` 去重

没有第 3 步，客户端会丢掉一个**正在进行中、尚未结束**的消息 —— 它既不完整也不可恢复。

### 4.3 保证

| | |
|---|---|
| 内容 | **不丢失** —— `llm_result` 兜底 |
| 增量粒度 | **不保证** —— 断线期间的文本增量不重放 |
| 持久事件 | 序号单调递增；可能重复，调用方按 `seq` 去重 |
| 流式事件 | 不带序号，直接应用 |

### 4.4 超出重放窗口

日志的保留期**就是**重放窗口。`from_seq` 落在窗口之外时**明确报错** —— 不静默从当前位置开始，那会让调用方以为消息连续，实际中间缺了一段。

### 4.5 多订阅者

同一个 Run 允许被多个客户端同时 `stream`，互不影响。

**推流是无状态的广播** —— 事件从日志来、从长连接来，N 个订阅者看到同一串事件，彼此不可见。每个连接有自己的游标（`from_seq`）和消息缓冲，各自在自己的 `message_started` 上重置。

**冲突全部发生在会话的写上，不在推流上** —— 见第 7 节。

实现上，每个 `manager` 副本为**每个正在被观看的 Run** 维护一个转发，再广播给连在它这台的订阅者；持有该 Run 的可能是另一台副本，由第 4.2 节第 2 步补上。

## 5. Worker 与重投

**一个 Run 在同一时刻只有一个 `worker`**，由派发与归属版本号（epoch）保证 —— 见 [06-internal-protocol.md](./06-internal-protocol.md) 2.2。

**崩溃后重投**：新的 `worker` 读日志重建状态 —— 依已完成的步骤恢复**会话上下文**（会话状态外置，见 [01-agent-platform-design.md](./01-agent-platform-design.md) 2.2）—— **从第一个没有 `_result` 的 `_call` 接着跑**。

**语义是 at-least-once。** 跑了一半的那一步会被重试：

- LLM 步骤重试无害
- **工具步骤可能重复副作用** —— 所以每个工具调用带上确定性**幂等键 `run_id + action_id`**（请求头），外部系统愿意配合就能去重

**不藏这条**：外部系统不支持幂等键时，重复副作用是真会发生的。这是 at-least-once 的定义，不是缺陷。

**重试有上限**，超了把 Run 判 `failed`。取值见 [11-roadmap.md](./11-roadmap.md) 待定项 12。

重试时重新写一行 `_call`：**`seq` 是新的，`action_id` 不变**。客户端因此收到一次新的 `message_started`，自然清空缓冲；幂等键也保持不变。

## 6. 取消

`cancel()` 是**请求**，不是动作：

- `manager` 落一个持久的**取消标志**，并沿长连接推一条取消（见 [06-internal-protocol.md](./06-internal-protocol.md) 2.4）
- `worker` 在**步骤边界**检查它们
- 正在飞的 LLM 调用能中断就中断，不能就在它结束后停
- **已经发出去的工具调用不撤回** —— 副作用留在那边
- 终态 `cancelled` 由 **`worker`** 追加一行日志 —— 它是这张表唯一的写者，`manager` 直接写会出现"已取消"后面还跟着 `tool_result`

`cancel()` **立即返回，不阻塞** —— 一次在飞的 LLM 调用可能几十秒。终态通过 `wait()` / `stream()` 观察。

## 7. 会话

**会话是单主体的：一个会话 = 一个调用主体的一段连续上下文。** 两个终端用户不会落进同一个会话，后端也不会把多个用户塞进一个会话。

主体是**创建它的那把 key 背后的人**：

| 提交方 | 主体 |
|---|---|
| 前端（临时 key） | 那个终端用户 —— 临时 key 上绑着 |
| 后端（永久 key） | 调用方本身 |

后端的主要场景是**定时任务**，而定时任务大多不传 `session`、不建会话 —— 所以实践里会话几乎全是前端的。

**主体只标归属与审计，不判权。** 它和 Agent 的责任人同一定位：标明这段对话是谁的，不含权限含义（见 [10-permissions.md](./10-permissions.md) 2.3）。

### 7.1 一个会话同一时刻只有一个活跃 Run

会话是一份共享的可变消息历史。两个 Run 并发跑，各自读到同一份历史、各自追加 —— 结果是交错或丢更新。

所以会话上有一个**活跃 Run 租约**，由 `manager` 在提交时抢占（它是 `execution_sessions` 的写者，见第 1 节）：**占着就拒绝**。客户端在运行中禁用发送键，服务端的拒绝是兜底 —— 第二句话本来是对着旧上下文写的，排队执行时那段上下文已经变了。

会话有自己的主体、一条要在事务里抢占的不变式、一段独立于 Run 的生命周期 —— **它是自己的聚合，Run 是它的子项**（见 [03-domain-model.md](./03-domain-model.md) 1.2）。

## 8. 上下文压缩

**消息历史只增不减，所以它一定会撞上模型的窗口。** 压缩是引擎自己的行为，按 Agent 上的配置触发 —— 主要作用于 `react`；DAG 是单趟的，节点之间传的是数据，不是一段不断增长的历史。

### 8.1 谁会被压

**只有会话的消息历史。**

**System Prompt 不在其中：**

- **它不是历史，是配置** —— 每次调用从快照重新渲染。压一个固定的东西省不出任何东西，只是白花一次模型调用。
- **它是指令面** —— 让模型摘要它，等于让模型改写这个 Agent 的规则。这与 [02-sdk-contract.md](./02-sdk-contract.md) 4.3 堵掉 `params` 是同一件事：**指令面只有配置者能写**，区别只在动手的是调用方还是引擎的摘要步骤。

System Prompt 的体量另有机制管 —— Skill 的正文按需拉取，常驻的只有名称与描述（见 [08-tools-and-skills.md](./08-tools-and-skills.md) 2.1）。**压缩不去替渐进披露干活。**

**`params` 在历史里，所以会被压掉** —— 但它是最近一次提交的参数，而压缩从最早的部分开始，它不会立刻丢。

### 8.2 阈值

**两个阈值都在 Agent 上配，谁先到算谁：**

| | 默认 | 防什么 |
|---|---|---|
| 模型窗口的占比 | 70% | 换模型 —— 纯绝对值会失效 |
| 绝对 token 数 | 300k | 成本 —— 大窗口装得下，账单装不下 |

**计的是会话累计的消息历史**，不是「下一次请求的预估」。

阈值是**配置**，进快照 —— 所以**改它要重新发布**（见 [07-release.md](./07-release.md) 第 1 节）。

### 8.3 方式：LLM 摘要

达到阈值时，把**最早的那部分会话消息**交给模型摘成一段，替换掉原文，**保留最近的部分**。这产生额外的模型调用，**它的 tokens 与成本照记** —— 否则成本算不准。

### 8.4 它落成一行日志

**压缩改变了模型看到的世界。** 不落一行日志，「模型为什么忘了前面」就无从回答 —— 而这个答案不在其他任何事件里。

**摘要全文落库，但不外发。** 其他事件的载荷是**结构化字段**，可以逐个决定发不发；**摘要是一段自由文本，切不开** —— 被压掉的消息里可能带着 Skill 正文（拉取后进入了会话上下文，那是配置的**内容**）。对外只给长度与范围（见 [02-sdk-contract.md](./02-sdk-contract.md) 6.5）。

**摘要因此成为这段历史的新起点**：后续运行读日志重建上下文时，读到 `context_compacted` 就用摘要替换掉它之前的消息 —— 日志仍然是唯一真相源。
