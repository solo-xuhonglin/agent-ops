# SDK 契约

- 状态：草稿（待评审）
- 日期：2026-10-08
- 范围：对外调用契约 —— SDK 表面、语义与保证
- 关联：[01-agent-platform-design.md](./01-agent-platform-design.md) 3.1
- 具体报文格式由 `contract/` 下的 OpenAPI 定义；**本文档定义 SDK 表面的语义与保证**

---

## 1. 定位

SDK 是平台对外的唯一入口。**它只认三样东西：key、输入、会话。**

平台内部有工具、Skill、凭据、编排方式、版本、节点这些概念 —— 它们全部不出现在契约里。这条是硬约束：**任何内部概念泄漏到 SDK，都会立刻变成无法修改的兼容性负担。**

---

## 2. 两个 SDK

| SDK | 语言与形态 | 身份 |
|---|---|---|
| 后端 | Python 包，同步接口 | Agent 的永久 key |
| 前端 | TypeScript 包，纯脚本库 | 换来的临时 key |

**前端 SDK 不提供 UI，不绑定任何框架**，浏览器与 Node 都能跑。它只做四件事：发请求、订阅流、管会话、转发令牌。

### 2.1 对称

两个 SDK 的**方法名、参数名、事件类型一一对应**。契约只定义一次，两种语言各实现一遍。本文示例用 Python 写法，TypeScript 侧同名同参，仅 `snake_case` → `camelCase`。

## 3. 调用模型

```
client = create_client(key, *, base_url=...)   # 后端给永久 key，前端给临时 key（临时 key 随第 7 节落地）

client.new_session()             → Session   # 新开一段对话
client.get_session(session_id)   → Session   # 取已有的
client.get_run(run_id)           → Run
client.get_agent()               → Agent     # 只含输入声明，见 4.1

session.submit(content, *, params=None, output_schema=None, request_id=None)  → Run
session.stream(*, from_run=None, from_seq=None)   → Iterator[Event]
session.id / session.current_run

run.wait(*, timeout=None)        → Result
run.cancel()
run.id / run.session_id / run.status
```

**两层：`client` 是 Agent 的句柄，`session` 是对话的句柄。**

`key` 决定租户、Agent 与主体 —— client 只绑这个。**会话是显式取的**：`new_session()` 新开，`get_session(id)` 取已有的（本地构造句柄，不发请求；不存在的会话在第一次使用时才报错）。**所有跟这段对话有关的动作都挂在 `session` 上**：提交、订阅、当前 Run。

**每个 Run 都属于一个会话。** 没有「不带会话的运行」—— 一次性的调用（定时任务）也新开一个，于是模型只有一条链：**会话 → 运行 → 日志**。

**`submit` 同步拿到 id**，但执行本身是异步的。平台在这一步就把 Run 行落下来（由 `manager` 写 —— 它是这两张表的写者，见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 1 节），再把句柄交回；否则调用方手上的 id 无法立刻用于 `get_run`。

**`submit` 永远只返回句柄。** 「怎么等」由句柄上的方法决定 —— 调用方不必在发送的那一刻就决定是阻塞、是流式、还是稍后再取。

这样安排带来三件事：

- **取结果**由句柄吸收，不再是"调哪个方法"。
- **上下文**由 `session` 对象表达 —— 它同时是**订阅的单位**（见 6.4）。
- **断线续传**与"稍后取结果"变成同一行代码：`client.get_run(run_id).wait()`。

扁平 API（`invoke` / `stream` 各一个方法）做不到最后一点 —— 那里"重新订阅"只能重发请求，会重复执行。

## 4. 输入与输出

`submit` 收两样东西：

| | 是什么 | 进哪里 |
|---|---|---|
| `content` | 这一次的对话内容 | 消息历史 |
| `params` | 键值对，这次调用的数据 | 渲染进给模型的消息 |

**`params` 存在的理由是：让「这次调用的数据」不混进自然语言。** 一个分析项目管理系统的 Agent 需要一个 project id —— 没有 `params`，就只能让模型从 `content` 里把它猜出来。

### 4.1 输入声明

Agent 定义上有一份**输入声明**，描述它接受哪些参数：

| 键 | 类型 | 必填 | **说明** | 默认值 |
|---|---|---|---|---|
| `project_id` | string | ✅ | 项目 ID，来自项目管理系统，形如 `PRJ-1042` | |
| `include_archived` | bool | | 是否包含已归档项目 | `false` |

**说明字段必填。** 模型对参数的理解完全来自它 —— 缺了它，`project_id` 就只是一串没有含义的字符。这与 Skill 的描述必填是同一条规则（见 [08-tools-and-skills.md](./08-tools-and-skills.md) 2.1）：**凡是给模型看的声明，说明字段必填。**

**声明对调用方可见。** 这是契约里第一次出现「接口声明」这类东西 —— 它不是配置的内容，而是配置**对外承诺的形状**。调用方必须知道有哪些键、哪些必填、什么格式，否则只能猜。经 `client.get_agent()` 拿到。

> 声明一旦对外就是兼容性负担 —— 改名、加必填、改类型都是破坏性变更。

### 4.2 渲染

`params` 渲染成**一段独立标注的数据块**，挂在这次调用的用户消息前面：

```
<输入参数>
- project_id（项目 ID，来自项目管理系统，形如 PRJ-1042）: PRJ-1042
- include_archived（是否包含已归档项目）: true
</输入参数>

分析这个项目的进度并生成概要
```

**渲染的是解析后的值。** 调用方没传、声明里有默认值的，填上默认值再渲染；没有默认值又没传的**整条不出现** —— 不渲染成一个空位，那会让模型以为传了值。

**它因此进入会话历史。** 第一轮传了 `project_id`，第三轮模型仍然看得到 —— 这是多轮会话能接上的前提。

### 4.3 它不会被当成指令

**`params` 只进用户消息，不进 System Prompt，也不进任何节点提示词。**

判据是**数据从哪来**：

| 来源 | 可信 | 能进指令面吗 |
|---|---|---|
| 图内部产生的数据（上游节点的输出） | ✅ 平台自己的运行结果 | 能 |
| **调用方给的 `params`** | ❌ 前端场景下就是终端用户 | **不能** |

`params` 进用户消息**不给调用方任何新权限** —— 它本来就能往 `content` 里写任何东西。而一旦进 System Prompt，就往调用方手里多递了一样东西：**改写这个 Agent 指令的能力**。前端用的是临时 key，那意味着任何一个终端用户都能重写系统提示词。

> 这是 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 3.1「引用外发，内容不外发」的另一面：那条管**什么往外发**，这条管**什么往指令面进**。

### 4.4 校验在提交时发生

`params` 不合法（缺必填、类型不对、传了没声明的键）→ `submit` **同步**抛 `ContractError`。

不能等跑起来才失败 —— 那样调用方拿到的是一个注定失败的 id。

校验发生在 `manager`（接 `submit` 的那个服务），它读的是 Agent 的**输入声明**这一个字段 —— **不是编排结构**，[01-agent-platform-design.md](./01-agent-platform-design.md) 3.3 那条约束不受影响。

### 4.5 输出：形状由调用方给

**输入的形状在配置里，输出的形状在调用方手里** —— 两个方向正好相反，而且这是对的：

| | 形状由谁定 | 为什么 |
|---|---|---|
| 输入 | 配置（输入声明） | 配置者写了 `{{params.project_id}}`，所以必须有 `project_id` —— 形状是从配置**反推**出来的 |
| 输出 | **调用方** | 要拿它去干什么，只有调用方知道 |

`submit` 的 `output_schema` 是一份 **JSON Schema** —— 它本来就是**代码里的东西**，跟着调用方的代码版本走，不走配置。

**不传就是纯文本**，`run.wait()` 拿到的：

| 传了 `output_schema` | `Result.output` |
|---|---|
| 否 | `str` —— 最后一次模型输出 |
| 是 | 按 schema 的结构化对象 |

**平台保证结构化时 `output` 符合 schema。**

**`output_schema` 随输入一起落进 `run_started`** —— 重投时新的 `worker` 要靠日志重建出原来那个请求（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 5 节）。

**失败不走 `Result`** —— `RunFailed` 在 `wait()` 时抛（见 6.6）。

> **DAG 节点之间的数据形状仍然是配置** —— 那是平台内部的事，调用方看不见。别和这里的「Agent 的对外输出」混为一谈。

## 5. 两个用法

调用方式**由调用方选，不由 Agent 的编排方式决定**。

### 5.1 对话式

```
client = create_client(key)
session = client.new_session()

events = session.stream()            # 订阅即建连：返回时已就绪，才不漏流式帧
session.submit("分析这个项目的进度", params={"project_id": "PRJ-1042"})
for event in events:                 # 订阅这段对话，空闲时也接着
    ...

session.submit("重点看延期的那几个")
```

### 5.2 任务式

```
client = create_client(key)
session = client.new_session()       # 定时任务：每次执行各开一个
run = session.submit("分析这个项目的进度，生成概要",
                     params={"project_id": "PRJ-1042"},
                     output_schema=REPORT_SCHEMA,
                     request_id="job-2026-10-09")

# 稍后，或者在另一个进程、重启之后
result = client.get_run(run.id).wait()
```

### 5.3 为什么不绑定编排方式

编排方式（ReAct / DAG）是内部实现，SDK 承诺调用方看不见它。若调用方式反过来由编排方式决定，会出现：

**一个 Agent 从 ReAct 迁到 DAG 时，调用方式跟着变，所有调用方都要改代码** —— 而这次迁移本该是一次纯内部替换。

所以两者保持独立，只在文档里给推荐搭配：**DAG 常配任务式，ReAct 常配对话式**，但不写进契约。

## 6. 契约要点

### 6.1 幂等

调用方生成 `request_id`。同一个 `(Agent, request_id)` 重复提交，返回**同一个运行**，不会产生第二次执行。

**`request_id` 标识的是一次逻辑调用，不是一类任务。** 定时任务必须把区分每一次的维度编进去（日期、调度实例 id）—— 复用固定的 id，第二天拿回的是第一天那个运行，**不报错、只是从此不再执行**。

**去重永不过期** —— 没有失效窗口。

**去重靠唯一索引** —— `(Agent, request_id)` 的唯一约束落在 `execution_runs` 上，由写这张表的 `manager` 在一次写入里判定，因此是原子的。

**队列的重投不是一次新提交** —— 它恢复的是同一个 Run，走的是另一条路（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 5 节）。

### 6.2 会话

**会话是显式取的**：`new_session()` 新开一个，`get_session(id)` 取已有的。**每个 Run 都属于一个会话** —— 一次性的调用（定时任务）也新开一个。

**一个会话只有一个主体** —— 前端提交的归那个终端用户，后端提交的归调用方自己。两个终端用户不会落进同一个会话。

**同一个会话同一时刻只有一个活跃 Run。** 运行中再提交会被拒绝，抛 `ConflictError`。**不同会话之间不互相阻塞** —— 所以定时任务每次各开一个，并发是天然的。

**订阅挂在会话上**（见 6.4）：连接建立时立刻推一次状态，之后按周期推状态、事件随时推。所以**空闲时也有一条连接** —— 另一个标签页提交的 Run 会立刻推过来。

`session.current_run` 给出正在跑的那个 Run（没有则为空）—— 页面刷新、第二个标签页打开时靠它接上（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 7.1）。

### 6.3 超时与取消

**`wait` 超时只是调用方不等了，运行继续。** 要停下来必须显式 `cancel()`。已产生的成本照记。超时单位：Python 秒，TypeScript 毫秒。

`run.status` 是这五个之一：`pending` / `running` / `succeeded` / `failed` / `cancelled`。**`wait` 超时不改变状态** —— 它仍是 `running`。

### 6.4 断线续传

事件带**单调递增的序号**。序号**在每个 Run 内独立编号**，从 1 开始 —— 它是 Run 的局部坐标，不是全局标识。

**订阅的单位是会话，所以游标是一对：`(run_id, seq)`。** 重连时把它交回去，服务端从那个位置接着推 —— 先把上一个 Run 剩下的部分推完，再接上当前这个。

**传输是 SSE**，用 `fetch` 流式读，不用原生 `EventSource` —— 后者设不了自定义请求头。见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 4.1。

**内容不丢失，增量粒度不保证。** 断线期间的文本增量不会重放，重连后可能等这一步结束、一次性拿到整段文本。顺序单调递增，但**可能重复** —— 两个 SDK 内部按 `(run_id, seq)` 去重后交付，并在断线时自动带游标重连。

> 这条对服务端是硬要求：**动作事实必须落成可重放的日志**，不能只走连接。见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 第 4 节。

### 6.5 事件

事件描述**这次运行做了什么**，与运行内部的动作一一对应。分两类：

**持久事件** —— 带序号，可重放：

| 事件 | 含义 |
|---|---|
| `run_started` | 运行开始 |
| `llm_call` / `llm_result` | 一次模型调用的起止，后者带完整消息、tokens、成本 |
| `tool_call` / `tool_result` | 一次工具调用的起止，带工具名与参数 / 结果或错误 |
| `agent_call` / `agent_result` | 一次子 Agent 调用的起止。**子运行的内部事件不外发** —— 事件流是父运行的序列 |
| `branch_taken` | 一次条件判定，带分支标签 |
| `context_compacted` | 一次上下文压缩 —— **引擎的行为，不是编排动作** —— 带压缩前后的长度与被压掉的范围；**摘要全文不外发** |
| `run_finished` / `run_failed` | 终态，带结果或错误详情 |

**流式事件** —— 不带序号，不重放，直接应用：

| 事件 | 含义 |
|---|---|
| `message_started` | 一条新消息开始 —— **清空当前消息缓冲**。重试与断线补发都会重发它 |
| `message_delta` | 追加文本 |

`_call` 与 `_result` 靠**动作 id** 配对 —— 不依赖严格交替（ReAct 一轮可以并发调多个工具，顺序会交错）。**未知事件类型必须忽略**，这样加一种动作类型就是纯增量。

### 6.6 错误

契约层面的错误由 SDK 抛异常；**执行失败是运行的状态，不是异常** —— 它在事件与运行状态上表达，`wait()` 时才转为异常。

| 异常 | 触发 |
|---|---|
| `AuthError` | key 无效，或已被重置 |
| `QuotaError` | 超出配额或触发限流。**v1 不产生** —— 配额只建不用（见 [10-permissions.md](./10-permissions.md) 2.2） |
| `ContractError` | 参数或协议不合法 |
| `ConflictError` | 会话里已有活跃的运行，这次提交被拒绝（见 6.2） |
| `NotFoundError` | 资源不存在或不归这个 key：404，如 `get_run` 的 id |
| `RunFailed` | 运行以失败结束（`wait` 时抛出） |
| `RunCancelled` | 运行被取消（`wait` 时抛出） |
| `Timeout` | `wait` 超时；**运行仍在继续** |

TypeScript 侧方法与参数名一一对应（`snake_case` → `camelCase`），异常名带 `Error` 后缀（`RunFailedError` 等）。

## 7. 鉴权

### 7.1 后端：永久 key

创建 Agent 时生成，只对那一个 Agent 有效，永久不过期。明文**只在生成时出现一次**，之后平台只存哈希。**平台不转交明文** —— 把它交给调用方是一次运维动作，由当时操作的人完成（创建时是编辑，重置时是管理员）。

**重置**由管理员操作，旧的立即失效。

### 7.2 前端：临时 key

**浏览器里不放永久 key。** 前端先找**调用方自己的后端**换一个临时 key：

```
前端 ──→ 调用方后端 ──(永久 key)──→ 平台
                                     ↓
前端 ←──── 临时 key（1 小时，只能调那一个 Agent）
```

换 key 时带上终端用户标识，**绑在临时 key 上**，之后前端不用再传。

**临时 key 是一张签名令牌** —— 内容是「哪个 Agent + 哪个终端用户 + 过期时间 + key 版本号」，平台用一把密钥签名。**它不落任何存储**：验证是算一次签名，不是查一次表。

**重置永久 key 就是把版本号 +1** —— 由它派生的临时 key 带着旧版本号，一并失效。重置的用意就是立刻断掉。

> 换 key 是平台的 HTTP 接口，由调用方后端调用 —— 它不属于前端 SDK。前端只需要知道去哪里拿这把 key。

### 7.3 终端用户标识只是审计

调用时带上来的用户标识**原样记录，不参与判权** —— 判权只看 key。平台不做单点登录，也不信任外部用户目录。

## 8. 屏蔽细节

对外是**一次运行的行为记录**，不是平台内部的结构。边界是：**引用外发，内容不外发** —— 唯一的例外是**输入声明**，它既不是「引用」也不是「内容」，是接口声明，对外可见（见第 4 节）。

| 不暴露 | 原因 |
|---|---|
| 编排方式是 ReAct 还是 DAG | 内部实现，改了不影响调用方 |
| 节点 id、边、图的形状 | 同上 —— 分支标签会外发，图形状不会 |
| 工具定义、Skill 正文、System Prompt | 配置的**内容**，不是运行的事实 |
| 凭据从哪来 | Agent 用自己在外部系统的账号，调用方不需要知道也不需要提供 |
| 版本号 | 平台决定用哪个版本 |
| 模型与参数 | 同上 |
| 子运行的内部事件 | 事件流是父运行的序列；子运行细节只在平台侧排障可见 |
| 保活与状态帧（`state`） | 平台内部机制 —— SDK 消化、兼作心跳，用户侧事件流只有事件 |

## 9. 待定项

1. **长任务的执行结果如何交付。** `wait()` 与 `stream()` 覆盖的都是"调用方在等"的场景。**定时任务是后端的主要场景，而它正是"没人等"的那一类** —— 靠轮询能用但不经济。可选做法：长轮询、回调地址、或者就维持轮询。**后续细化。**
2. **运行日志保留多久。** 它就是重放窗口。游标落在窗口之外直接报错，调用方只能重新拉运行状态、拿不到中间过程（见 [05-execution-and-streaming.md](./05-execution-and-streaming.md) 4.4）。保留期与成本直接相关 —— 日志同时是运行记录、观测数据与重放窗口，一处策略管三件事。
3. **前端临时 key 怎么续期。** 临时 key 只有 1 小时，页面开着超过 1 小时就会失效。可选做法：调用方自己重建 client（简单，但每处都要写一遍）；或者 client 接受一个取 key 的回调，SDK 在**认证过期**时重取、用同一个 `request_id` 重放（调用方无感，但 SDK 多了一条自动重试路径，得限定它只在这种错误上触发）。
4. **前端要不要收紧到不能带 `output_schema`。** v1 可以带 —— schema 是调用方给的，而前端那一份终端用户改得到，用字段说明做注入可以把配置内容掏进一个数据字段。这与「平台不替调用方管它自己的终端用户」（见 [10-permissions.md](./10-permissions.md) 2.3）一致，所以接受。要收紧的话，最省事的是前端 SDK 不带这个参数，代价是破坏两个 SDK 的对称（见 2.1）。
