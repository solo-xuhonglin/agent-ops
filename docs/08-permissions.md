# 权限

- 状态：草稿（待评审）
- 日期：2026-10-08
- 范围：团队成员在配置面的角色，与外部程序在调用面的 key
- 关联：[01-agent-platform-design.md](./01-agent-platform-design.md) 3.6

**权限完全由程序实现**，判定发生在应用层。

---

## 1. 配置面：团队成员三种角色

**判据：这个动作会不会影响团队之外的东西？** 会 → 管理员；全在团队内 → 编辑。

| 角色 | 管什么 | 具体动作 |
|---|---|---|
| **管理员** | **边界与身份** | 团队成员、租户凭据、重置调用 key、导入导出 |
| **编辑** | **团队内部的内容** | 建 / 改 / **发布 / 回滚 / 归档** Agent、工具、Skill |
| **只读** | 查看 | |

**没有独立的运行角色。** 运行不是团队成员的动作 —— 跑 Agent 的是外部程序（见第 2 节）。

**发布归编辑。** 它是"配置一个 Agent"这个闭环的收尾 —— 编辑改完草稿让它生效，而不是另找一个人点按钮。**回滚同理**：它是应急动作，多一道手续只会让恢复更慢。

**管理员管的是跨出团队边界的动作** —— 谁能进这个团队、Agent 在外部系统里是谁、谁可以调用、配置整体进出。这些改错了，影响的不只是一个 Agent。

**责任人只是元数据。** 标明这个 Agent 谁创建、谁维护、出事找谁，**不含任何权限含义** —— "谁能改"完全由角色决定。

## 2. 调用面：key 即授权

**对外只暴露 Agent。** Tool 和 Skill 不可直接调用，只能被 Agent 引用 —— 这砍掉了一大类越权面。

### 2.1 两种 key

| | 谁用 | 怎么来 | 有效期 | 范围 |
|---|---|---|---|---|
| 永久 key | 后端 | 创建 Agent 时生成 | 永久 | 那一个 Agent |
| 临时 key | 前端 | 调用方后端拿永久 key 换 | 1 小时 | 那一个 Agent |

**持有 key 就是授权。** 没有独立的授权表，也没有"应用"这一层中间实体 —— 平台由 key 反查出租户与 Agent，认证与授权一步完成。

**一个 Agent 一把永久 key。** 代价是所有后端调用方共用一把、出了事分不清是谁。当前接受；将来需要按调用方区分时，再放开成多把。

**重置**是管理员操作，旧的**立即失效**。

### 2.2 判定

**key 有效 → 放行。** 判定链只有这一步。

**配额是租户级的，v1 只建不用** —— 模型落在 `iam`，判定链不卡这一条。

### 2.3 终端用户标识

调用时带上来的终端用户标识**原样记录，只用于审计**：

- **不参与任何判权** —— 判权只看 key
- 后端调用**可选**传；前端在换临时 key 时绑定，之后不用再传
- 平台不做单点登录，也不信任外部用户目录

> 为什么不判权：外部系统的权限是按**账号**给的，而调外部系统的是 Agent 自己的账号（见 [07-credentials.md](./07-credentials.md) 第 1 节）。终端用户在这条链路上本来就代表不了任何权限。

## 3. 已知缺口：工具级权限

**v1 只有资源级权限，没有工具级权限。** Agent 能做什么，调用它的外部调用方就间接能做什么 —— Agent 拿自己的权限替调用方做事，而调用方不一定有同样的权限（confused deputy）。

自用场景下可接受：维护者本来就是全权限。**升级触发条件是「第一个外部调用方调用一个会写外部系统的 Agent」**，届时需要三件事：工具声明所需权限范围、只有具备该范围的调用方才能把它绑进 Agent、调用时校验发起者是否具备该范围。高风险工具还需人工审批。
