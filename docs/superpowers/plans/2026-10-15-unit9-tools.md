# Unit 9: HTTP Tools and the Tool Spec Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Agents can call HTTP tools: a Tool spec model, request templating with credential placeholders, real execution with idempotency keys and response trimming, and the engine's ReAct loop closed with `tool_call`/`tool_result` pairing and `max_iterations`.

**Architecture:** `ToolSpec` lives in `shared/spec.py` (name, required description, JSON-schema `parameters`, HTTP request template with `{{args.x}}`/`{{credential}}` placeholders, `credential` name, `response_max_bytes`) and `AgentSpec.tools: list[ToolSpec] = []`. `worker/tool_exec.py` renders the template (credential resolved from `CREDENTIAL_<NAME>` env in v1 — the secrets store replaces the resolver in unit 13), sends with an `Idempotency-Key: <run_id>:<action_id>` header and a timeout, trims the response. The engine loops: LLM call with model-facing tool definitions → scripted `tool_calls` executed sequentially (row before request, row after result/error) → tool results appended as provider-shaped messages → next LLM call, until a tool-free answer or `max_iterations` → `run_failed`. Open `tool_call` resumes like an open `llm_call`: same action_id (same idempotency key), arguments replayed from the log.

**Tech Stack:** Python only; httpx (already a dependency) for outbound tool requests; in-process HTTP fakes as the mock external services.

**Spec:** docs/08-tools-and-skills.md §1.1 (parameter templates, trimming, timeouts), docs/05-execution-and-streaming.md §2 (tool_call/tool_result payloads), §3.1 (credential injection happens after logging — credentials must not leave any gaps), §5 (idempotency key run_id+action_id), docs/09-credentials.md §4 (credential unavailable → run fails explicitly).

## Global Constraints

- Credential values never enter logs, events, or engine memory beyond the outbound request; `tool_call` rows carry the tool name and the MODEL's arguments only; header templates are logged pre-injection.
- Credential resolution failure fails the run explicitly (`run_failed`), never a silent skip (docs/09 §4).
- One HTTP attempt per execution; retries are the sweep's at-least-once re-dispatch (idempotency key stays stable because action_id does).
- Tool errors are `tool_result` errors the model sees and may recover from; only iteration exhaustion fails the run.
- `max_iterations` counts LLM calls; exceeding → `run_failed`, status check per docs/02 §6.3.
- Sequential tool execution within a round (no parallelism in v1); cancel is checked between tools and after each LLM stream.
- Prior runs still rebuild as user + final assistant only (tool rounds stay trace-only) — ruling, revisit with real providers.
- Comments/logs English; tests only touch `*_test` DB and in-process mock servers; PIPESTATUS-guarded verifications.

## Review Focus

1. **Credential never leaks** — logged tool_call carries model arguments and the pre-injection template; the resolved value appears only in the outbound HTTP request. Pinned in Task 2 (render keeps template; server records injected header) and Task 3 (row payload assertions).
2. **Idempotency key stable across re-dispatch** — retried open tool_call re-sends the same `<run_id>:<action_id>` header. Pinned in Task 3 (fake server records the header; resume re-executes with same key).
3. **Response trimming caps the context** — oversized responses truncated with a marker. Pinned in Task 2.
4. **Runaway loops stop as failures** — model demanding tools forever hits `max_iterations` → `run_failed`. Pinned in Task 3.
5. **Tool errors are recoverable results** — a 500/tool error becomes a `tool_result` error and the model gets another turn. Pinned in Task 3.

### Task 2: worker — request rendering and HTTP execution

**Files:**
- Create: `worker/src/worker/tool_exec.py`
- Test: `worker/tests/test_tool_exec.py`

**Interfaces:**
- Produces: `resolve_credential(name: str) -> str` — v1 reads `CREDENTIAL_<NAME>` (upper); missing → raise `CredentialUnavailable` (Task 3 turns it into `run_failed`).
- Produces: `render_request(tool: ToolSpec, arguments: dict, credential: str | None) -> tuple[str, str, dict, str | None]` — (method, url, headers, body): `{{args.x}}` substituted from arguments anywhere in url/headers/body; `{{credential}}` substituted with the resolved value; unresolved `{{args.*}}` → `ToolError` (the model sent bad arguments).
- Produces: `execute_tool(run_id: str, action_id: str, tool: ToolSpec, arguments: dict) -> ToolOutcome` where `ToolOutcome = {"ok": bool, "result": str | None, "error": str | None, "duration_ms": int, "truncated": bool}`: httpx request (timeout 10s) with header `Idempotency-Key: f"{run_id}:{action_id}"`; response body trimmed to `response_max_bytes` (`truncated: true`); HTTP >=400 → `ok False` with the status in `error`; connection errors/timeouts → `ok False`.

- [ ] **Step 1: Failing tests** (in-process `FakeUpstream` http.server recording method/path/headers/body, scripted responses):

  - credential: header template `Authorization: Bearer {{credential}}` — upstream sees the env value while `render_request` output handed to logging (the TEMPLATE, not the value) stays `{{credential}}` (Review Focus 1 — assert the tool spec's own headers unchanged after execution).

  - 500 → `ok False, error` mentioning the status; connection refused → `ok False`.
  - body larger than `response_max_bytes` → result trimmed, `truncated True` (Review Focus 3).
  - unresolved `{{args.x}}` → `ToolError`; missing credential env → `CredentialUnavailable`.

### Task 3: engine — the tool loop

**Files:**
- Modify: `worker/src/worker/engine.py`, `worker/src/worker/llm.py` (stream signature)
- Test: `worker/tests/test_engine_tools.py`

**Interfaces:**
- Consumes: Task 1 `ToolSpec.to_definition()`, Task 2 `execute_tool`/`resolve_credential`/exceptions.
- Produces: `LlmClient.stream(messages, *, tools: list[dict], model_id, model_params)`; `FakeLlm` records `tools` in `.calls`.
- Produces: engine changes —
  - fresh path sends `tools=[t.to_definition() for t in spec.tools]` to every LLM call;
  - `llm_result.tool_calls` non-empty → for each `{"name", "arguments"}`: `action_id = uuid4`; row `tool_call {"tool", "arguments", "idempotency_key": f"{run_id}:{action_id}"}`; credential resolution failure → `run_failed {"error": ...}` and stop; `execute_tool`; row `tool_result {"result"/"error", "duration_ms", "truncated"}`; messages append assistant `{role, tool_calls: [{id: action_id, name, arguments}]}` then `{role: "tool", tool_call_id: action_id, content: result-or-error}` per tool;
  - loop back to the next LLM call (which streams normally); cancel checked before each tool and between LLM streams;
  - iterations ≥ `spec.max_iterations` while the model still demands tools → `run_failed {"error": "max iterations exceeded"}`;
  - resume: `pending` scan extended to tool pairs; an open `tool_call` re-executes the HTTP call with the logged arguments and SAME action_id (new `tool_call` row first, per docs/05 §5 retry shape).
- Produces: `worker/tool_exec.py` re-exported exceptions `ToolError`, `CredentialUnavailable`.

  - resume with open `tool_call` (pre-seeded rows) → NEW `tool_call` row, same action_id, fake upstream records the same `Idempotency-Key` twice-driven once (Review Focus 2), then completes.
  - credential declared, env missing → `run_failed` mentioning the credential name; no tool_result row.
  - `FakeLlm.calls[0]` received `tools=[definition]`.
